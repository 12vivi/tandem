## 3. 发现

1. **tandem 的 GPU 路径瓶颈在调度和内核启动开销，而不在算力。** 单路每 token 27 ms，而 0.6B 模型按显存带宽算的理论值约 1.5 ms，只用到了约 6%。这是 P1 要解决的问题：CUDA Graph、FlashInfer、融合算子、GPU 常驻的无同步主循环。
2. **同为 FP32 时，tandem 单请求解码达到 llama.cpp 的 86%，TTFT 更低（432 vs 575 ms）。** 但并发 4 时只有 49%：参考版 attention 用的是"补齐后统一计算"的方式，加上 Python 循环开销，批处理扩展性差。P2 的 C++ CPU 执行器和 CPU attention 内核要解决这个问题。
3. **CPU 上量化是最大的杠杆。** llama.cpp 用 Q4_K_M 比 FP32 快 4–5 倍。CPU 解码受内存带宽限制，量化减少了每个 token 要读的字节数。tandem 在 CPU 上要追平，必须接入量化内核（P2：ggml / IQK / kt-kernel）。
4. **修正带宽估算。** 这台机器的 CPU 有效读带宽约 27 GB/s，是 PCIe（12.9 GB/s）的约 2.1 倍：
   - 比 `tandem probe` 测出的 19.2 GB/s 拷贝带宽高，因为拷贝带宽把读和写都算进去了；
   - 也低于最初按 35–40 GB/s 估算的约 3 倍。

   所以在这台机器上，"缺失专家在 CPU 上算"比"经 PCIe 换入"快约 2 倍，S1/S3 的收益上限按这个比例重新估算。

## 4. 尚未完成与阻塞项

| 项 | 状态 | 原因 / 方案 |
|---|---|---|
| vLLM 基线 | 未做 | 最新 0.33 只支持 CUDA 13（需要驱动 ≥580）。0.32（torch 2.13，有 CUDA 12.9 构建）预计能靠 CUDA 小版本兼容在驱动 550 上运行，但离线下载约 4.5 GB，按当前链路约需 3 小时；报告中要注明落后最新版一个版本 |
| SGLang 基线 | 未做 | 0.5.23 的 wheel 要求 glibc ≥2.34，服务器是 2.31，而且依赖 CUDA 13，原生装不上。可选：找较旧的版本；用 Docker 镜像（需要 sudo 或加入 docker 组，镜像传输量更大）；升级系统和驱动 |
| llama.cpp GPU 版 | 未做 | 服务器没有 nvcc，需要 CUDA Toolkit（约数 GB） |
| 大模型场景（S1 / S3 / S4） | 未做 | 需要 8–60 GB 的模型，例如 Qwen3-8B 16 GB、Qwen3-30B-A3B FP8 约 31 GB、70B 4-bit 约 40 GB。服务器不能联网，从本机经 VPN 传输只有约 1.3 MB/s，每个模型要 3.5–9 小时 |
| S2（超大 MoE） | 不适用 | 这台机器只有 62 GB 内存，需要 512 GB 以上的服务器 |

**建议**：先解决服务器联网，并把驱动升级到 580 以上（需要你用 sudo 操作；如果机器多人共用，先和其他使用者确认）；或者用移动硬盘拷贝模型。否则，大模型场景和最新版 vLLM / SGLang 的对比，可以改在能联网、驱动较新的云 GPU 上做，这台 3090 用于日常开发和小模型测试。

## 5. 复现

- GPU 基线：在服务器上启动 `tandem serve --device cuda --dtype bfloat16`，再运行 `benchmarks/bench_serving.py`（输入 512 / 输出 128，并发 1,4,16）。
- CPU 基线：`benchmarks/p0/run_cpu_baseline.sh`（路径按服务器目录布局写死，使用前请按实际环境修改）。
- 原始结果：`benchmarks/results/p0-server-3090.jsonl`（该目录不进入版本库）。
