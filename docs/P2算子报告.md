# P2 算子优化报告（2026-11-13）

> 对应设计方案 §8 P2、§5.2 的 A1 / A2：在 batch 1–8 的 decode 上超过对手。
>
> 对手数据沿用 P0 基线报告 §6（vLLM 0.32.0、SGLang 0.5.10，过渡版本）。A 场景每格都和三种对手配置里最快的比，几乎都是 SGLang + torch.compile。

## 1. 结论

- **A2（Qwen3-8B-AWQ）**：batch 1 / 4 / 8 的 TPOT 是最强对手的 **1.092 / 1.069 / 1.048 倍**。
  - 目标 ≥1.05 倍：batch 1、4 达到，batch 8 差 0.02 ms（0.2%）；
  - batch 8 只看 decode 一步（ITL p50）已经快 6%（7.86 vs 8.33 ms），差距在 TPOT 里别的请求的 prefill 停顿（§5.3）；
  - 输出和 vLLM 逐 token 一致（5 个提示词各 64 token，320/320）；
  - 4096 提示词的 TTFT 只有对手的 0.79–0.93 倍，原因是 prefill 每个分块都要先反量化全部权重（§5.3）。
- **A1（BF16）**：
  - Qwen3-0.6B：1.075 / 1.055 / 1.038 倍，目标 ≥1.2 倍，**未达到**；
  - Qwen3-1.7B：1.039 / 1.048 / 1.023 倍，目标 ≥1.05 倍，**未达到**，差 0.2%–2.7%。
- **离带宽下限多远**（下限按 P0 的算法：每 token 读的权重字节 ÷ 实测拷贝带宽 788 GB/s）：batch 1 时 0.6B 是下限的 1.33 倍（对手 1.43），1.7B 是 1.04 倍（对手 1.08），8B AWQ 是 1.07 倍（对手 1.17）。1.7B 的目标（≤4.53 ms）只比下限高约 3%，0.6B 剩下的差距主要在几百个小内核之间的边界上（§5.2）。
- **判定：P2 部分达成**。A2 的 batch 1、4 达标，batch 8 差 0.2%；A1 未达标。剩下的工作见 §6，其中 A1 冲 1.2 倍要靠持久化内核，按设计方案 §5.2 作为研究线，不阻塞 P3。
- **正确性**：GPU 上 92 项测试全部通过（每个自写内核都和参考实现逐配置对比，端到端贪心输出和 FP32 参考一致，允许近似平局）。

## 2. 条件

- **负载**（设计方案 §1.3、P0 基线报告 §6）：随机提示词，512 进 / 512 出，并发 1、4、8，看 TPOT p50；另测 4096 进 / 16 出，看 TTFT。每档 max(8, 4×并发) 条请求，重复 3 次取中位数。
- **对手配置**：vLLM 默认（已开 torch.compile、完整 CUDA graph、异步调度）；SGLang 默认，以及加 `--enable-torch-compile --torch-compile-max-bs 8`。
- **模型**：A1 是 Qwen3-0.6B、1.7B（BF16）；A2 是 Qwen3-8B-AWQ（4 bit，group 128，AutoAWQ gemm 格式，`--dtype float16`）。
- **tandem 0.2.0.dev0**：P1 的配置（prefill 优先、token 预算 2048、decode CUDA graph 到 batch 64、overlap 主循环）加上 P2 的内核，全部默认打开，各有一个关闭开关（`--no-small-batch-gemv`、`--no-small-batch-attention`、`--no-small-batch-norm`、`TANDEM_W4_FUSE_ACT=0`）。
- **环境**：同 P1（RTX 3090、驱动 550；torch 2.14.1+cu126、FlashInfer 0.6.7、Triton 3.8；CUDA 扩展用 nvcc 12.4、gcc 11.2 编译）。

## 4. 做了什么

细节（做法、原因、数据、可能的追问）在 `docs/面试复习.md` §3.6–3.9，这里只列要点。

### 4.1 Triton 小 batch GEMV（A1，提交 `6b88705`）

- CUDA 核心版（batch 1–2）和 tensor core 版（x 补到 16 行，batch 4–8），按（N, K, batch）查表，只在比 cuBLAS 快 3% 以上的形状上用；
- 内核比 cuBLAS 快 1.03–1.52 倍（`benchmarks/bench_gemv.py`，在 CUDA graph 里轮换 ≥96 MB 的权重测）。

### 4.2 Triton split-KV decode attention（A1，提交 `831ecba`）

- 每个程序处理一个（请求、KV 头）和一段页，GQA 组的 query 头放在寄存器里；最后一个完成的程序用 acq_rel 原子计数器在同一个内核里合并；
- 只在 GQA 2、batch 1–2 时启用：单路 512 上下文 11.6 → 7.8 µs/层，batch 4 起和 FlashInfer 互有胜负。

### 4.3 AWQ 4 bit（A2，提交 `6b76a60`、`dd675db`）

- 加载：量化层直接创建 4 bit 缓冲区，不分配 dense 权重；qkv、gate_up 沿输出维拼接；加载后在 GPU 上一次性重排；
- 布局：每个 int32 存 8 个连续的 k，半字节顺序就是 LOP3 反量化需要的顺序；一个 lane 一次 16 字节加载正好是一行的一个量化组；
- decode 内核（CUDA C++，`python/tandem/csrc/w4_gemv.cu`）：
  - `w4_gemv`：CUDA 核心，LOP3 把 4 bit 值直接拼进 half2(1024, 1024)，batch 1 时用；
  - `w4_mma`：`mma.m16n8k16`，权重当 A 操作数、batch 当 n = 8 那一边（swap AB，batch ≤ 8 不补零），权重从显存直接进 A 片段；用一个 A、B 共用的 k 置换让 x 也能 16 字节加载；权重用 `ld.global.nc.L1::no_allocate` 读，L1 留给 x；
  - 8B 四个投影 batch 1→8 每层合计只从 123 µs 涨到 127 µs，batch 8 时比 cuBLAS 跑 FP16 权重快 3.5–4.1 倍；
- prefill：反量化成 FP16 后交给 cuBLAS。

### 4.4 decode 步瘦身（A2 为主，提交 `dd675db`）

- gate_up 的 SwiGLU 放进 `w4_mma` 的收尾（加载时把 gate、up 的行交错），省掉激活内核；
- batch ≥ 8（GQA ≥ 4）多捕获一个不切分 KV 的 CUDA graph，每步按最长上下文选；8B BF16 上开关对照 4 格都快 0.2%；
- 残差加 RMSNorm 换成每行一个程序的 Triton 内核，所有 decode batch 快 1.2–1.7 倍，对 0.6B、1.7B、8B 都生效；
- 全贪心的步在 FP16 logits 上做 argmax；embedding 按行数选实现；8B lm_head 走 Triton GEMV（快 2–3%，低于 3% 的门槛，破例收录，理由写在配置表里）。

### 4.5 试过但没有采用

- **把 norm 和激活融合进 GEMV 的前处理**：微基准 batch 1 每对省 0.4–0.9 µs，放进 decode graph 后融合的 GEMV 变慢了差不多同样多，0.6B 单路 2.01 → 2.04 ms，关掉（面试复习 §3.7）；
- **FlashInfer 的 `fixed_split_size`**：微基准里的"固定切分"其实等于不切分，而且文档说明它不保证兼容 CUDA graph，改用 `disable_split_kv` 加双 graph；
- **GQA 4 用 Triton split-KV**：batch 4–8 时不比 FlashInfer 快（`p2-attn-8b.jsonl`）。

## 5. 剖析

### 5.1 8B AWQ 每个 decode 步（nsys，µs，`p2-profile-awq.jsonl`）

| 部分 | tandem batch 1 | SGLang + compile batch 1 | tandem batch 8（tensor core 第一版） | tandem batch 8（SwiGLU 融合、不切分后） |
|---|---|---|---|---|
| 量化线性层 | 4460 | 4867（Marlin） | 4668 | 4678 |
| lm_head | 1382 | 1378 | 1412 | 1430 |
| attention | 507 | 493 | 1572 | 1517 |
| 激活 | 118 | 51 | 125 | 0（融合） |
| norm、RoPE、写 KV、采样等 | 266 | 约 420 | 348 | 351 |
| 整步 | 6801 | 7329 | 8187 | 8031 |

- 这张表之后又加了 Triton norm（batch 8 每步约省 0.07 ms）和 lm_head、argmax、embedding 的小改动，没有再剖析；
- SGLang 在 nsys 下跑 batch 8 时服务崩溃，没有它 batch 8 的分解。

### 5.2 A1 0.6B 为什么离 1.2 倍还远

- 单路一步约 2.0 ms，其中权重读取按拷贝带宽算约 1.5 ms（P0 的下限），其余是约 300 个内核各自的启动和尾部延迟、以及 attention 的固定开销（P1 剖析：每层约 11–12 µs，和上下文长度基本无关）；
- 目标 1.78 ms 是下限的 1.19 倍，要把内核边界上的损耗去掉一大半，单个内核再优化已经不够，需要持久化内核（设计方案 §2.2 的 MPK 路线）。

### 5.3 A2 batch 8：TPOT 和 decode 步的差别

- batch 8 时 TPOT p50（8.53 ms）比 ITL p50（7.86 ms）多 0.67 ms；SGLang 是 8.94 vs 8.33，多 0.61 ms；
- 多出来的是别的请求的 prefill 步：8 个 512 token 的请求要分两步 prefill（预算 2048），先 prefill 的请求要等第二步做完才能继续 decode，这段停顿摊进它们的 TPOT；
- tandem 的 prefill 步更长：AWQ 的每个 prefill 分块都要把全部权重反量化成 FP16（每块约 26 ms，4096 token 的 prefill 里约占 5%，512 token 的 prefill 里约占 18%），对手用的是直接读 4 bit 的 Marlin GEMM；
- 同一个原因也让 4096 提示词的 TTFT 只有对手的 0.79–0.93 倍。

### 5.4 步与步之间的空档

- 8B AWQ batch 8 每步 GPU 空闲约 0.75%：graph 内部约 380 个内核之间合计约 32 µs，步与步衔接处约 24 µs；
- 衔接处的几段是：graph 启动延迟 8.3 µs，argmax、拷回 token、下一步输入拷贝之间各 5–6 µs，属于拷贝引擎和计算引擎交接的延迟。

## 7. 复现

服务器上（环境变量同 P0 基线报告 §10；CUDA 扩展第一次加载时编译，需要 `CUDA_HOME` 和 nvcc、gcc 11 在 PATH 里）：

```bash
PY=~/tandem/.venv/bin/python
T=(--engine tandem --python $PY --env LD_LIBRARY_PATH=/usr/local/gcc-11.2/lib64 --env CUDA_HOME=/usr/local/cuda-12.4
   --env PATH=/usr/local/cuda-12.4/bin:/usr/local/gcc-11.2/bin:/usr/bin:/bin --env HF_HUB_OFFLINE=1 --env TRANSFORMERS_OFFLINE=1)
$PY benchmarks/run_matrix.py "${T[@]}" --model ~/models/Qwen3-8B-AWQ --served-name qwen3-8b-awq --dtype float16 \
  --shapes 512x512,4096x16 --levels 1,4,8 --scenario A2 --tag tandem-0.2.0.dev0-w4h --save benchmarks/results/p2-a.jsonl
$PY benchmarks/run_matrix.py "${T[@]}" --model ~/models/Qwen3-0.6B --served-name qwen3-0.6b \
  --shapes 512x512,4096x16 --levels 1,4,8 --scenario A1 --tag tandem-0.2.0.dev0-norm --save benchmarks/results/p2-a.jsonl
PATH=/usr/local/cuda-12.4/bin:$PATH $PY benchmarks/profile_engine.py "${T[@]}" --model ~/models/Qwen3-8B-AWQ \
  --served-name qwen3-8b-awq --dtype float16 --batches 1,8 --input-len 768 --margin-tokens 512 \
  --save benchmarks/results/p2-profile-awq.jsonl
```

内核微基准见 `benchmarks/README.md` 的"内核微基准"一节（`bench_gemv.py`、`bench_decode_attn.py`、`bench_w4.py`、`bench_norm.py`）。原始结果在 `benchmarks/results/`（不进版本库），文件清单见 `docs/面试复习.md` §7。

和 vLLM 的逐 token 对比：`benchmarks/results/logs/awq-compare-w4h.out`（服务器上），脚本是同一个提示词集分别用 tandem 的 `LLMEngine` 和 vLLM 的 OpenAI 接口贪心生成 64 个 token，再逐个比较。
