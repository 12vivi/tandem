## 0. 摘要

**正面硬拼不现实的场景：数据中心 GPU、模型放得进显存、高并发。**

- vLLM 0.33 和 SGLang 0.5.23 已经用上了业界最强的内核，例如 FlashInfer、FA3/FA4、Marlin、DeepGEMM。
- 运行时也是最新的，包括 vLLM 的 Model Runner V2 无同步主循环、SGLang 的 Spec V2，以及 DFlash 并行草稿 [vLLM][vLLM-MRV2][SGLang-SpecV2]。
- 新框架用同一批内核，最多只能做到持平，所以本方案在这里只要求"不落后"。

**单卡 + CPU 是两者的结构性空白。**

- vLLM 的权重卸载只是把权重经 PCIe 流式搬到 GPU，不在 CPU 上计算 [vLLM-CPU]。
- 官方 SGLang 在 2026 年 10 月合入了 Paged Experts，但计算同样只在 GPU 上做。它的 PR 写明还不支持把缺失的专家放到 CPU 上算，并且在短 prompt 的 TTFT、小显存加并发两种情况下输给了 llama.cpp [SGLang-PE]。
- SGLang 的 CPU 后端只针对带 AMX 的 Xeon [SGLang-CPU]。
- 要用 KTransformers 的 CPU 内核，必须安装 kvcache-ai 维护的 fork `sglang-kt` [KT-README]。

**已有研究证明，这块空白里可以超过现有最好的方案。**

- OSDI'26 的一个 CPU-GPU 混合系统，decode 速度是 KTransformers 的 1.25 倍，长 prompt 的 prefill 达到 1,200 tok/s [CloudGradeMoE]。
- 按专家负载逐 step 决定"搬到 GPU 算"还是"留在 CPU 算"，相对最强基线 decode 提升 39.5%、prefill 提升 51.9% [AdaptiveExpert]。
- 面向卸载场景设计的投机解码，还能再带来 1.5–2.5 倍收益 [Specter][SpecMoEOff]。

**本方案的做法**

以 Mini-SGLang（MIT 许可）作为 GPU 控制面的骨架 [MiniSGLang]，在上面叠加：
- GPU 常驻、无同步的主循环，参考 vLLM MRV2；
- 统一的"放置计划"和屋顶线代价模型；
- **三路径专家执行**：每个 step 自适应地选择让专家常驻 GPU、换入 GPU 或在 CPU 上计算；
- 带宽优先的 CPU 内核，复用 kt-kernel 和 ik_llama.cpp，目标是用到 80% 以上的 DRAM 带宽；
- 流式 prefill，以及节点内的 prefill/decode 分离；
- 卸载感知的自适应投机解码；
- GPU / CPU / SSD 三级 KV 缓存。

**预期收益**（各场景定义见 §1.2，依据见 §5，P0 实测后修订）

| 场景 | 目标 | 置信度 |
|---|---|---|
| S1 消费级卡跑略超显存的 MoE | 每个测试格都不低于 SGLang Paged Experts 和 llama.cpp 中较好的那个 | 中高 |
| S2 超大 MoE + 服务器 CPU | decode ≥1.2×、长 prompt prefill ≥1.5× SGLang+KTransformers | 中 |
| S3 稠密模型超出显存 | ≥3× vLLM/SGLang，≥1.3× llama.cpp | 高 / 中 |
| S4 KV 受限的在线服务 | goodput ≥1.15× | 中低 |
| S5 单用户低延迟 | TPOT 快 ≥1.2× | 低（研究性质） |
| S6 纯 CPU | 非 AMX 平台 ≥1.5× vLLM CPU | 中 |

**投入估计**：按 3–4 名熟悉 CUDA、C++ 和系统的工程师计，约 7 个月达到主要目标。P0 先花 2–3 周复现全部基线，得到"要超过的那根线"。

## 1. 目标与边界

### 1.1 目标

- 运行环境是单机、单张 NVIDIA GPU（Ampere 及以上）加主机 CPU。同一套引擎支持三种模式：
  - **G 模式**：模型完全放进显存。
  - **H 模式（异构）**：权重、KV 或计算在 CPU 和 GPU 之间切分。典型情况是 MoE 的冷专家、超出显存的稠密层，以及部分 decode attention。
  - **C 模式**：纯 CPU，覆盖 x86 的 AMX / AVX-512 / AVX2 和 Arm 的 NEON / SVE。
- 功能上提供 OpenAI 兼容 API、连续批处理、前缀缓存、投机解码和结构化输出。
- **默认无损**：输出与参考实现（HF Transformers）在数值容差内一致。有损技术（Expert Deferral、稀疏注意力、激进量化）必须显式开启。
- 在 §1.2 定义的场景里，以可复现的基准测试超过 vLLM 和 SGLang 的最新稳定版。

### 1.2 "性能比 vLLM / SGLang 强"的可验证定义

| 场景 | 描述 | 主要指标 | 对手（版本固定，见 §6） |
|---|---|---|---|
| **S1** | 消费级卡（8–16 GB）跑略超显存的 MoE，如 Qwen3-30B-A3B（int4 / FP8） | decode tok/s（并发 1 和 4）、TTFT | SGLang Paged Experts；llama.cpp（调优 `--n-cpu-moe` / `--fit`） |
| **S2** | 超大 MoE（DeepSeek-V3/R1 671B、Qwen3-235B-A22B），单卡 24–32 GB + 双路 Xeon/EPYC 大内存 | prefill tok/s、decode tok/s（并发 1–8）、32K prompt 的 TTFT | SGLang+KTransformers（`sglang-kt`）、KTransformers、llama.cpp / ik_llama.cpp |
| **S3** | 稠密模型超出显存（70B 级 4-bit 跑在 24–32 GB 卡上） | decode tok/s、TTFT | llama.cpp `-ngl`；vLLM / SGLang 的权重卸载 |
| **S4** | 模型放得下，但 KV 限制了并发（RTX 4090/5090、L40S 级卡做在线服务） | SLO 约束下的 goodput、TPOT p99 | vLLM、SGLang |
| **S5** | 单用户或低并发交互 | TPOT、TTFT | vLLM、SGLang（各自最佳投机配置）、ExLlamaV3、llama.cpp |
| **S6** | 纯 CPU：带 AMX 的 Xeon，以及不带 AMX 的 x86 桌面/服务器 | prefill / decode tok/s、并发吞吐 | SGLang CPU（仅 AMX）、vLLM CPU、llama.cpp / ik_llama.cpp |

**非目标（v1 不做）**：
- 多卡 TP / EP / PP、多机部署、跨机 PD 分离。
- 在 H100/B200 这类数据中心卡上、模型完全放得下的高并发场景全面超越。这里只要求达到 vLLM/SGLang 的 0.95 倍以上，即持平（理由见 §2.4）。

## 2. 调研：现状与机会

### 2.1 两个主要对手的现状（2026 年 11 月）

| 能力 | vLLM 0.33.0（2026-11-02） | SGLang 0.5.23（2026-10-30） |
|---|---|---|
| 运行时 | V1 引擎。async scheduling 自 v0.14（2026-01）起默认开启。Model Runner V2 自 v0.29 起默认：请求状态常驻 GPU，Triton 构造输入，连同投机解码在内都不做 host 同步 [vLLM][vLLM-MRV2] | overlap（零开销）调度 [SGLang-v0.4]。Spec V2（投机解码与 overlap 结合）自 v0.5.11 起默认。分段 CUDA Graph 自 v0.5.10 起默认 [SGLang] |
| 前缀缓存 / KV 分层 | 哈希式自动前缀缓存（APC）；CPU / 磁盘 / 对象存储多级 KV 卸载；LMCache 等连接器 | RadixAttention；HiCache（GPU → 主机内存 → 存储三级）[HiCache] |
| 投机解码 | EAGLE / EAGLE-3、MTP、suffix、GPU n-gram、DFlash、P-EAGLE、DSpark。自适应验证目前只支持 DSpark，且只在 SM100 上可用 [DSpark] | EAGLE / EAGLE-3、MTP、DFlash、topk>1 的草稿树；n-gram 模式会关闭 overlap 调度 |
| 量化 | FP8、NVFP4 KV（SM8x/90/12x）、MXFP4、Marlin、Machete、QuTLASS；GGUF 已移出核心代码，改为插件 | FP8、AWQ / GPTQ（Marlin）、MXFP4 / NVFP4、W8A8 |
| 超显存权重 | `--cpu-offload-gb`（UVA，每次前向都经 PCIe 读权重）；Weight Offloading V2（带预取）。**都不在 CPU 上计算** [vLLM-CPU] | `--cpu-offload-gb`；**Paged Experts**（v0.5.23，可选）：每层 K 个专家槽常驻 GPU，全部专家放在 pinned 内存里按需拷入，**计算仍在 GPU 上** [SGLang-PE] |
| CPU 后端 | 一个 x86 wheel 按 AVX2 / AVX-512 / AMX 分派；支持 Arm（KleidiAI） | 只针对 AMX Xeon 优化，官方说明在其他 x86 上会很慢 [SGLang-CPU] |
| CPU-GPU 混合计算 | 无 | 必须安装 kvcache-ai 的 fork `sglang-kt` 才能用 kt-kernel [KT-README] |
| 低延迟 megakernel | 只覆盖个别模型和硬件（如 GB300 上的 DeepSeek-V4.1-Flash、AMD MI3xx 上的 `--monokernel`） | 可选插件，只覆盖 GB300 / MI350X 上的 DeepSeek-V4.1-Flash |
| Windows | 不原生支持，需要 WSL | 不原生支持 |

**Paged Experts 的官方实测**（来源：SGLang PR #42557 [SGLang-PE]）

测试条件：Qwen3-30B-A3B，ShareGPT prompt，输出 256 token，量化按字节数对齐，llama.cpp 调到最佳 `--n-cpu-moe`。

| 硬件 / 精度 | 指标 | Paged Experts | llama.cpp（调优后） | SGLang `--cpu-offload-gb` |
|---|---|---|---|---|
| RTX 5070 Ti 16 GB / int4 | 单流 decode | **205.6 tok/s** | 194.4 | 16.6 |
| 同上 | 并发 4 吞吐 | **374–387** | 312 | 62 |
| 同上 | 短 prompt TTFT | 89 ms | **68 ms** | 147 ms |
| RTX 5070 Ti 16 GB / FP8 | 单流 decode | **87.7** | 45.2 | — |
| RTX 4070 Laptop 8 GB / int4（WSL2） | 单流 decode | 30.6–32.9 | 23.0–32.4 | — |
| 同上 | 并发 4（K 较小） | 11–12 | **41** | — |
| 同上 | 短 prompt TTFT | 872–953 ms | **620 ms** | — |

这张表说明了两件事：
- 显存够放下大部分专家时（16 GB 卡），GPU 换入的方式更好。
- 显存紧张、并发又上来时（8 GB 卡），在 CPU 上计算缺失的专家反而快约 3.5 倍。
- 能逐 step 在两者之间做选择的系统，理论上每一格都能拿到两者中较好的结果。这是 S1 的立论依据。

### 2.3 学术前沿速览

- **运行时开销**
  - vLLM v0.5.3 时，GPU 只有 38% 的时间在计算 [vLLM-perf24]。
  - MRV2 在小模型上带来 +56% [vLLM-MRV2]，Spec V2 带来 +33% [SGLang-SpecV2]。
  - 主机 CPU 核数不足会让 TTFT 恶化 1.47–7.11 倍 [HostCPU]；同机运行的其他进程可使吞吐下降 78.8% [CoLocation]。
  - **对本项目的意义：H 模式下 CPU 计算线程会占满核心，控制面必须有独占的核。**
- **投机解码**
  - 并行草稿成为新前沿：DFlash（ICML'26，在 Qwen3-4B 上比 EAGLE-3 再快约 1.5 倍）、P-EAGLE、DSpark [DFlash][P-EAGLE][DSpark]。
  - DSpark 每个 step 选择要验证多少个草稿 token，在并发 1–256 的范围内都保持在帕累托前沿。
  - 后缀树草稿在 Agent 类负载上最高 5.3 倍 [SuffixDecoding]。
  - 卸载场景的专门方法：SpecExec、Dovetail、SpecMoEOff、Specter [SpecExec][Dovetail][SpecMoEOff][Specter]。
- **单卡调度**
  - 分块 prefill [Sarathi-Serve]。
  - 单卡内的 nano-batch 重叠 [NanoFlow]。
  - 在单卡上按 SM 划分 prefill 和 decode：Nexus 相对 vLLM 吞吐最高 2.2 倍。这些都是研究原型，对比的是 2025 年版本的基线 [Nexus][semi-PD][DuetServe]。
- **内核**
  - FlashInfer 支持 SM75–SM121，包括 RTX 50 系列 [FlashInfer]。
  - FA3 只支持 Hopper；FA4 在 sm_120 上的路径退化为 SM80 风格 [FA4]。
  - sm_86/89/120 没有 WGMMA/TMEM，每个 block 的共享内存只有 99 KB，FA3、DeepGEMM、Machete、FlashMLA 都用不上，需要单独调优的内核路径。
  - QuTLASS 在 RTX 5090 上用 NVFP4，端到端是 FP16 的 4 倍 [QuTLASS]。
- **KV 缓存**
  - HiCache 在主机侧用 page-first 布局，并用 GPU 辅助的拷贝内核，比 `cudaMemcpyAsync` 最多快 3 倍 [HiCache]。
  - 对原生稀疏注意力（DSA/NSA）的模型，HiSparse 让放在主机内存里的 KV 可以精确使用 [HiSparse]。

### 2.4 结论：哪里能赢，哪里不硬拼

**有证据能赢的场景**

1. **S1/S2（MoE 超出显存）**：组合使用 CPU 计算、GPU 换入和逐 step 的自适应分配，加上带宽优先的 CPU 内核、流式 prefill 和卸载感知的投机解码。证据见 §2.1–2.2。
2. **S3（稠密模型超出显存）**：vLLM/SGLang 每生成一个 token 都要经 PCIe 搬一遍权重。而 CPU 内存带宽比 PCIe 高 2–12 倍：
   - CPU 内存：桌面约 100 GB/s；服务器每路实测约 220 GB/s，标称 600 GB/s 以上；
   - PCIe：Gen4 实测 24.9 GB/s，Gen5 约 50 GB/s。
3. **S6（纯 CPU）**：SGLang CPU 只服务 AMX 平台；vLLM CPU 没有找到与 llama.cpp 的公开对比。在非 AMX 平台上，真正的对手是 llama.cpp 和 ik_llama.cpp。

**有机会但证据较弱的场景**
- **S4**：NEO 在弱 GPU 上收益很大，但在 H100 上只有 +14%。
- **S5**：消费级卡上还没有人做过 megakernel。

**不硬拼的场景**：数据中心卡、模型放得下、高并发。对手的内核与本项目同源，而且迭代极快（vLLM 0.33 一个版本有 927 个 commit、389 位贡献者；SGLang 0.5.23 有 1,007 个 PR、257 位贡献者）。这里的目标定为持平。

## 3. 总体架构

```

                              | ZMQ: requests                   | ZMQ: token ids
                +-------------v---------------------------------+--------------+
                | Engine Core process   (control-plane cores reserved)         |
                |  +---------------+  +------------------+  +----------------+ |
                |  | Scheduler     |  | KV/Prefix Cache  |  | Placement      | |
                |  | GPU-resident  |  | radix tree +     |  | Planner        | |
                |  | request state |  | paged blocks     |  | roofline cost  | |
                |  | overlap loop  |  | GPU<->CPU<->SSD  |  | expert stats   | |
                |  +-------+-------+  +--------+---------+  +-------+--------+ |
                |          +-------------------+--------------------+          |
                |                     +--------v--------+                      |
                |   spec-decode  ---> |  Model Runner   |                      |
                |   controller        +---+---------+---+                      |
                |                         |         |                          |
                |  +----------------------v--+   +--v------------------------+ |
                |  | GPU executor            |   | CPU executor (C++ pools)  | |
                |  | CUDA Graph              |   | per-NUMA thread pools     | |
                |  | FlashInfer / FA attn    |   | AMX/AVX-512/AVX2/NEON     | |
```

### 3.1 进程与线程模型

- **API 进程**：负责 HTTP/SSE、分词、chat template、增量反分词和语法编译。
  - 它与引擎进程分离，避免 GIL 争用拖慢调度循环。vLLM V1 和 SGLang 都这样拆分 [vLLM-V1][SGLang]。
  - 两个进程之间用 ZMQ 通信。
- **引擎进程的主循环**参考 vLLM MRV2 和 SGLang Spec V2 [vLLM-MRV2][SGLang-SpecV2]：
  - 请求状态表常驻 GPU，输入张量直接在 GPU 上构造；
  - 输出经旁路 stream 异步拷回主机；
  - 采样、拒绝采样和语法 mask 都不触发 host 同步；
  - 调度器始终领先 GPU 一个 step（overlap）。
- **CPU 核的划分**：
  - 控制面（调度、分词、语法）独占若干物理核，与 CPU 计算线程池隔离 [HostCPU][CoLocation]；
  - 计算线程池按 NUMA 节点各建一个 [KTransformers]。

### 3.2 统一的"放置计划"（Placement Plan）

G、H、C 三种模式不写三套代码。规划器生成一份放置计划，Model Runner 按计划选择内核。

**计划包含三部分：**
- **张量放置**：每个权重张量的位置是 `GPU`、`CPU`、`CPU 且可换入` 三者之一。
- **专家执行路径**：每个 step、每个专家，在三条路径中选一条（细节见 §4.6）：
  - GPU 常驻；
  - 换入 GPU（pinned → HBM，换入后进入专家缓存）；
  - CPU 就地计算。
- **KV 放置**：每个请求的 KV 页在显存还是在 CPU 内存，决定了它的 decode attention 在哪里算。

**规划器的输入**
- **硬件画像**：首次启动时用微基准实测，包括：
  - 带宽：HBM、PCIe H2D/D2H（pinned 内存）、每个 NUMA 节点的 DRAM；
  - 算力：各 ISA 下 CPU 的 GEMM 算力、GPU 的 GEMM 算力。
- **模型配置**。
- **在线的专家激活统计**。

**思路来源**：
- FlexGen 用线性规划搜索卸载策略 [FlexGen]；
- MoE-Lightning 用分层屋顶线模型 [MoE-Lightning]；
- Fiddler 用延迟模型决定专家在哪里执行 [Fiddler]；
- 自适应专家分配让 CPU 路径和 PCIe 路径同时结束 [AdaptiveExpert]。

### 3.3 一个 decode step 的时序（H 模式，MoE）

```
GPU stream : [attn L]->[router L]->[shared + resident + paged-in experts L]------>[combine]->[attn L+1] ...
PCIe       :                  +-->[page-in high-load missing experts]--^
CPU pools  :                  +-->[low-load missing experts (AMX/AVX GEMV)]--------^
                                   D2H hidden states (KB) / H2D expert outputs (KB)
```

- 路由（router）在 GPU 上算。跨 PCIe 的只有隐状态和专家输出，每 token 每层几 KB；只有被选中换入的专家才搬运权重。
- 整个 step 由 CUDA Graph 捕获。图中插入 host 回调节点（`cudaLaunchHostFunc`）来提交 CPU 任务和同步 [KTransformers]。
- **Expert Deferral**（把部分专家的结果推迟一层再合并，以实现跨层重叠）会造成平均 ≤0.5% 的精度损失 [KTransformers]，所以只作为可选项。
- 有并发时，采用双 batch 的 attention–MoE 重叠：一个 batch 在 GPU 上做 attention，另一个 batch 在 CPU 上算专家 [CloudGradeMoE]。

### 3.4 prefill 路径（H 模式）

```
PCIe : [stream experts L+1][stream experts L+2] ...      (pinned, double-buffered)
GPU  : [compute L        ][compute L+1        ] ...
CPU  : [low-load experts of L (if below T*)  ] ...
```

- 长 prompt 走流式加载 prefill（SLP）[CloudGradeMoE]：专家权重按层流式上传、在 GPU 上计算。同类思路还有 [llama.cpp] 的大 batch 算子卸载和 MoE-Lightning 的 CGOPipe [MoE-Lightning]。
- 短 prompt，或者某专家分到的 token 数低于阈值 T*（定义见 §4.6）时，留在 CPU 上算。
- **节点内 PD 分离**：prefill 和 decode 分属两组执行资源，零拷贝共享同一份权重，长 prefill 不会拖慢在途的 decode [CloudGradeMoE]。

### 4.1 API 前端

- 提供 OpenAI 兼容的 `/v1/chat/completions` 和 `/v1/completions`，支持 SSE 流式、logprobs、`response_format`（JSON Schema）和 tools。
- 分词用 HF `tokenizers` [HF-tokenizers]。chat template 用 Jinja2，与 HF 模板保持一致。增量反分词沿用骨架的实现。
- 语法在 API 进程里编译（带缓存），编译结果随请求一起传给引擎 [XGrammar]。

### 4.2 调度器

- **连续批处理** [Orca]，以及带 token 预算的**分块 prefill** [Sarathi-Serve]。每个 step 先排 decode，再用剩余预算排 prefill 分块。
- **无同步、领先一步的主循环**（§3.1）[vLLM-MRV2][SGLang-SpecV2]。
  - 与 SGLang 的 n-gram 模式不同，所有草稿方式都保持 overlap。SGLang 的 n-gram 模式会关闭 overlap。
- **前缀感知排序**：缓存压力大时，按最长前缀匹配（LPM）优先 [SGLang]。
- **以 goodput 为目标**：
  - 请求带 SLO（TTFT、TPOT）和优先级 [DistServe]；
  - 可选 VTC 公平调度 [VTC]；
  - 可选按输出长度排序做近似最短作业优先 [LTR]；
  - 可选按每个请求的 SLO 设定投机深度 [AdaServe]。
- **抢占**：把 KV 换出到 CPU pinned 内存，或者丢弃后重算，由代价模型选择。单机上经 PCIe 换出 1 GB KV 约需 20–40 ms。
- **异构感知**：调度器向规划器询问本 step 的 CPU 和 GPU 负载，据此选择 batch 的组成，例如哪些请求的 attention 放到 CPU 上算 [NEO]。
- **按需划分 SM（P4）**：当延迟模型预测 TBT 会超标时，再把 SM 分给 prefill 和 decode 两条流 [DuetServe][Nexus]。
- batch 大小对齐 CUDA Graph 的捕获档位。

### 4.3 KV 缓存

- **分页 KV** [PagedAttention]，页表格式与 FlashInfer 的 paged KV 布局一致 [FlashInfer]。
  - 页大小依所用 attention 内核的约束选择，默认 16 或 32。
- **Radix 树前缀缓存**，配 LRU 淘汰 [SGLang]。
- **三级缓存**：GPU 显存（L1）→ CPU pinned 内存（L2）→ NVMe（L3，可选）[HiCache][LMCache][CachedAttention]。
  - 主机侧用 page-first 布局，GPU 侧用 layer-first 布局；
  - 用 GPU 辅助的拷贝内核在两种布局间搬运；
  - 计算第 i 层时预取第 i+1 层的 KV。
  - 单机 DRAM 通常是显存的 5–40 倍，多轮对话和 Agent 场景的前缀命中率会明显提高。
- **KV 量化**：
  - FP8 为默认推荐；
  - NVFP4 KV 用于 Blackwell 和 Ada；
  - INT4 KV 采用 KIVI / QServe 的做法 [KIVI][QServe]，需要定制 attention 内核，放在 P3 之后。
- **H-KV 模式**：部分请求的 KV 常驻 CPU 内存，它们的 decode attention 由 CPU attention 内核计算，再用 log-sum-exp 与 GPU 部分合并 [NEO][InplaceKV]。

### 4.4 GPU 执行器

- **模型定义**：PyTorch 模块加自定义算子。加载权重时按目标内核重排布局，例如 Marlin 要求的重排。
- **CUDA Graph**：
  - 纯 decode 的 batch 按档位整图捕获；
  - 混合 batch 用分段图，attention 在图外执行（与 vLLM 的 FULL_AND_PIECEWISE 相同）[vLLM]；
  - H 模式下，图里包含 host 回调节点（§3.3）。
- **按 GPU 架构选择内核**（参考调研推荐的内核栈）：

| 架构 | batch=1 延迟 | 高吞吐（batch ≥32） |
|---|---|---|
| Ampere（sm_80/86） | W4A16 Marlin；EXL3（2–4 bpw）；FlashInfer split-KV decode | Marlin 用到 batch 约 64–128，再往上用 FP16 或 INT8 W8A8；QServe W4A8KV4 |
| Ada（sm_89） | 同 Ampere，加 FP8 KV | FP8 W8A8（实际无损）[FP8-Study] |
| Hopper（sm_90） | Marlin / Machete；FA3 或 FlashInfer decode | DeepGEMM / CUTLASS 块缩放 FP8；FA3/FA4 prefill |
| Blackwell 消费级（sm_120） | 4-bit 仅量化权重（Marlin 走 PTX 或 NVFP4 权重）；FlashInfer / b12x decode | NVFP4 W4A4（CUTLASS-sm120 / QuTLASS，配合 MR-GPTQ 量化） |
| Blackwell 数据中心（sm_100） | NVFP4 / INT4 仅量化权重；FA4 或 FlashInfer | NVFP4 W4A4 + MXFP8 作为精度兜底；FA4 prefill |

- **MoE**：
  - Triton / FlashInfer fused MoE 和 Marlin-MoE [Marlin][FlashInfer]；
  - 把路由和 token 对齐融合进 MoE 内核 [MPK]；
  - H 模式下 GPU 只算共享专家、常驻专家和换入专家。
- **小算子融合与采样**：
  - RMSNorm + 残差、SiLU-and-mul、RoPE + KV 写入，复用 FlashInfer 的内核；
  - 采样用 FlashInfer 的免排序实现 [FlashInfer-Sampling]。
- **S5 延迟模式（P4，研究性质）**：
  - batch 1–8 的 decode 用持久化 megakernel [MPK][Hazy-Megakernel]，优先填补"消费级 sm_86/89/120 没有 megakernel"这一空白。
  - 这一项的风险见 §9。

### 4.5 CPU 执行器

C++20 库，用 nanobind 绑定 Python，运行时按 ISA 分派内核：

| ISA | 典型 CPU | 内核来源 | 用途 |
|---|---|---|---|
| AMX（BF16 / INT8 / INT4） | Xeon 第 4–6 代 | kt-kernel [KTransformers]；SGLang CPU 的做法 [SGLang-CPU] | 专家分到的 token 较多时（每专家 >4 token）和 prefill |
| AVX-512（VNNI / BF16 / FP8 GEMV） | EPYC Zen4/Zen5、Xeon | kt-kernel 的 AVX-512 路径；IQK [ik_llama.cpp]；按 [CloudGradeMoE] 重写的带宽优先 GEMV | decode（每专家 ≤4 token） |
| AVX2（+AVX-VNNI） | 消费级 Intel / AMD | ggml [llama.cpp]、IQK、tinyBLAS [llamafile]；kt-kernel 的 AVX2 后端 | 兼容兜底；本机 i5-1240P 属于这一档 |
| NEON / SVE（+I8MM） | Grace、Graviton、Apple M 系列 | KleidiAI [KleidiAI]、ggml | Arm 平台 |
| 低比特查表 | 不限 | T-MAC [T-MAC]、bitnet.cpp [bitnet.cpp] | ≤3 bit 或三值模型 |

- **带宽优先**：decode 受内存带宽限制，内核验收标准是"实测带宽 ≥80% 标称"，而不是 FLOPS。
  - OSDI'26 系统的 FP8 GEMV 跑到 947 GB/s [CloudGradeMoE]，SGLang CPU 的 MoE 达到 85% [SGLang-CPU]；而 oneDNN 在 MoE 上只有 AMX 峰值的约 7% [KTransformers]。
  - 不依赖已归档的 IPEX 和 xFasterTransformer。
- **NUMA**：
  - 每个专家矩阵跨 socket 切分，最后做 reduce-scatter。跨 socket 带宽约为本地的 57%（125 vs 220 GB/s）[KTransformers]；
  - 权重放在 2 MB 大页里；
  - 启动时做带宽饱和测试，决定 decode 用多少线程。
- **CPU attention 内核**：
  - 用于 H-KV 模式和 C 模式；
  - 支持分页 KV，以及 BF16 / FP16 / FP8 KV；
  - 参考 NEO 和 vLLM CPU 后端 [NEO][vLLM-CPU]。
- **C 模式**：
  - 整个模型在 CPU 执行器上运行，调度器与其他模式共用；
  - 投机解码在 C 模式下收益尤其大（§4.7）。

### 4.6 异构执行层（核心差异化）

**(a) 显存分配顺序**
1. 按目标并发预留 KV；
2. attention、norm、embedding、lm_head；
3. 共享专家 / 稠密 FFN；
4. 专家缓存槽：按激活频率和打分决定放哪些专家，支持在线替换 [HybriMoE][DALI]；
5. 其余权重放在 CPU（pinned 内存，或者 mmap 加 SSD 层）。
   - SGLang Paged Experts 要求能 pin 住全部专家，也没有磁盘层 [SGLang-PE]。本项目支持"主机内存小于全部专家"的配置，把冷专家放在 mmap 或 SSD 上，参考 [fastllm][FlexGen]。

**(b) 三路径分配**

设第 e 个专家的权重为 Nₑ 个参数、每参数 b 字节，本 step 分到 nₑ 个 token：

```
GPU 常驻 : t ≈ max(Nₑ·b / B_hbm , 2·Nₑ·nₑ / P_gpu)
换入 GPU : t ≈ Nₑ·b / B_pcie + t_gpu      # 换入后留在缓存，未来命中按复用概率折算收益
CPU 计算 : t ≈ max(Nₑ·b / B_dram , 2·Nₑ·nₑ / P_cpu)
目标     : 选择 {换入集合, CPU 集合}，使 PCIe 路径与 CPU 路径同时结束，再加上缓存价值项
交叉点   : T* ≈ P_cpu · b / (2 · B_pcie)  # nₑ > T* 时换入或流式更快
```

- 分配方法来自 [AdaptiveExpert]（让两条路径同时结束）以及 [HybriMoE][DALI]（缓存价值）。

**估算示例**（仅作示意，实际以启动时实测为准）：

- **服务器**
  - 参数：每路 AMX MoE 内核实测 21.3 TFLOPS [KTransformers]，PCIe 5.0 实测约 50 GB/s，INT4（b≈0.56）。
  - 得到 T*≈120 token/专家；FP8 下约 210。
  - DeepSeek-V3 是 256 个专家选 8 个，所以整层流式只有在 prompt 达到约 4K–7K token 时才更快。这与 [CloudGradeMoE] 只在长 prompt 上做流式 prefill 一致。
- **桌面**
  - 参数：AVX2 有效算力约 1 TFLOPS，PCIe 4.0 实测 24.9 GB/s，INT4。
  - 得到 T*≈11 token/专家，换算到 Qwen3-30B-A3B（128 选 8）约为 180 token。
  - 这和 llama.cpp 的 32-token 阈值在同一量级。
- **decode**
  - 每个专家分到的 token 很少：并发 32、128 选 8 时平均只有 2 个。CPU 路径受 DRAM 带宽限制，而 B_dram/B_pcie 在服务器上约 4–12 倍、桌面上约 2–4 倍，所以缺失的专家通常留在 CPU 算。
  - 显存较宽裕、缓存命中率高时，按需换入更好，对应 [SGLang-PE] 在 16 GB 卡上的结果。
  - 显存紧张又有并发时，CPU 计算更好，对应 llama.cpp 在 8 GB 卡、并发 4 时的结果。
  - 三路径分配让两种情况都能取到较好的那一边。

**(c) 其他机制**
- **CUDA Graph 与 CPU 任务同步**：通过 host 回调节点提交和同步 CPU 任务 [KTransformers]。
- **双 batch 的 attention–MoE 重叠**：在 OSDI'26 系统中带来 +50% 吞吐、延迟增加 <15% [CloudGradeMoE]。
- **流式 prefill 与节点内 PD 分离**（§3.4）[CloudGradeMoE]。
- **离线大批量模式**：按模块累积 token 再批量计算 [MoE-Gen]，比 FlexGen、MoE-Lightning、DeepSpeed 高 8–31 倍吞吐。
- **稠密模型超出显存（S3）**：
  - 前若干层常驻 GPU；
  - 其余层在 batch 小时由 CPU 计算，batch 大时流式上传；
  - 配合大规模投机树摊薄每步读权重的成本（§4.7）。
- **KV 卸载（S4）**：采用 NEO 的非对称流水 [NEO]。
  - 收益对 GPU/CPU 算力比很敏感：弱 GPU 上最高 7.5 倍，H100 上 +14%。
  - 因此由规划器根据实测的硬件画像决定是否开启。

### 4.7 投机解码

**草稿来源**
- 并行草稿：DFlash（MIT）、P-EAGLE [DFlash][P-EAGLE]；
- EAGLE-3 [EAGLE-3]；
- 模型自带的 MTP 头 [DeepSeek-V3]；
- 无模型的后缀树 / n-gram 草稿 [SuffixDecoding][PromptLookup]。
- 后缀索引直接建在 radix 前缀树上，与模型草稿的候选按匹配长度合并。这是本项目的设计，尚无文献验证。

**验证**
- 用标准的投机采样规则保证输出分布不变（无损）[SpecDec]；
- 用树形验证 [SpecInfer]，通过 FlashInfer 的自定义 mask 实现。

**自适应验证预算**
- 每个 step 选择要验证的 token 数，使"每单位 step 成本的期望接受 token 数"最大 [DSpark]。
- step 成本取自规划器的代价模型，包含 CPU 和 PCIe 部分。
- vLLM 的自适应验证目前只支持 DSpark、只在 SM100 上可用；本项目推广到所有草稿方式和 Ampere / Ada / sm_120。

**卸载感知（H / C 模式）**
- 当 CPU 侧受内存带宽限制时，一次验证多个 token 几乎不增加成本，应该使用大得多的投机树 [SpecExec][Sequoia]。
- 粗算：服务器 AMX 约 20 TFLOPS，读 20 GB INT4 权重约需 100 ms，而算一个 token 只需约 3.6 ms，所以几十个 token 的验证几乎"免费"；桌面 AVX2 大约只能"免费"验证 3 个。
- MoE 模型的验证 token 越多，激活的专家并集越大，所以要按专家并集来规划草稿 [Specter][SpecMoEOff]。
- 闲置的 GPU 用来跑草稿 [Dovetail]。

**收益与成本**
- 预期收益：
  - SpecMoEOff 的 decode 最高 2.5 倍；
  - Specter 的 TPOT 平均 1.50 倍；
  - Dovetail 在 13B 模型上 1.79–10.1 倍。
- 主要成本：每个模型需要一个训练好的草稿模型。

### 4.8 量化与模型格式

- **输入格式**：
  - HF safetensors，包括 BF16、FP8、AWQ [AWQ]、GPTQ [GPTQ]、compressed-tensors；
  - GGUF k-quants / i-quants [GGUF]，用来直接复用社区已量化的模型。
- **加载时按设备转换布局**：
  - GPU 侧：转成 Marlin 重排的 INT4、FP8 或 NVFP4；
  - CPU 侧：转成 AMX tile 打包的格式，或 ggml 块量化格式；
  - 同一个专家需要在 CPU 和 GPU 两条路径之间切换时，优先选两边内核都能直接读取的格式，避免双份存储。
- **推荐默认**：
  - 低并发：W4A16；
  - 高并发：FP8 W8A8，实际无损 [FP8-Study]；
  - Blackwell：NVFP4 配合 MR-GPTQ [QuTLASS]。FP4 并不天然优于 INT4，必须保留 FP8 作为兜底；
  - 要把 30–70B 塞进 24–32 GB 的极限场景：EXL3 [QTIP][ExLlamaV3] 或 GGUF i-quants。
- **许可证注意**：
  - QTIP 的参考代码是 GPL-3.0，SpinQuant 的代码是 CC-BY-NC-4.0，两者都不直接引入；
  - EXL3 用 ExLlamaV3 的 MIT 实现。
- 任何量化配置都必须通过 §4.11 的精度回归。

### 4.9 结构化输出与采样

- 后端：XGrammar / XGrammar-2 [XGrammar][XGrammar-2]，llguidance 作为备选 [llguidance]。
- mask 在控制面独占的核上计算，与 GPU 前向重叠；在 C 模式下这一点尤其重要，否则 mask 计算会与模型争抢 CPU 核。
- 惩罚项、logprobs、停止条件的语义与 OpenAI API 保持一致。

### 4.10 长上下文（可选）

- **精确方案**：
  - 分块 prefill + KV 分层 + 按层预取；
  - 按序列把 attention 切分到 CPU 和 GPU [InplaceKV]；
  - 原生稀疏注意力模型用 HiSparse 式的主机 KV [HiSparse]。
- **近似方案**（默认关闭）：ShadowKV [ShadowKV]、MagicPIG [MagicPIG]、RetrievalAttention [RetrievalAttention]。

### 4.11 可观测性与正确性

- **可观测性**：
  - Prometheus 指标；
  - NVTX 区间；
  - 每个 step 的 CPU / GPU / PCIe 时间线导出为 Chrome trace；
  - 放置计划和专家命中率可导出。
- **正确性测试**：
  - 逐层激活与 HF Transformers 对比（BF16 下余弦相似度 >0.999）；
  - 相对 BF16 参考的 KL 散度或 logprob 差；
  - 固定 prompt 集上的贪心输出一致；
  - lm-eval-harness 上的 GSM8K / MMLU 与参考相差在 ±0.5 分以内。
- **有损开关**（Expert Deferral、近似注意力）开启时必须同时报告精度。

### 6.4 工具与公平性

**客户端**：
- 所有引擎统一用 AIPerf [AIPerf] 或参数相同的 `vllm bench serve`，并以多进程模式运行。单进程 asyncio 客户端在高负载下会抬高测得的 TTFT 和 TPOT [BenchBias]。
- 再用各引擎自带的工具交叉验证一次。

**工具默认值的坑**：
- `vllm bench serve` 默认不预热，也不忽略 EOS；
- `sglang bench_serving` 默认预热 1 次，并且忽略 EOS（除非加 `--disable-ignore-eos`）。

**公平性规则**：
1. 使用相同的权重，量化按字节对齐，或者报告每权重的位数；
2. KV dtype 和容量、max_model_len、max-num-seqs 保持一致；
3. 分块大小要么统一，要么报告各引擎调到最佳后的值；
4. 除前缀专项测试外，关闭前缀缓存或在两次运行之间清空缓存；
5. chat template 和采样参数保持一致；
6. 投机解码要么全部关闭，要么全部开启并使用同一种草稿，同时报告接受率；
7. 每个基线都调到最佳，例如扫描 llama.cpp 的 `--n-cpu-moe` 并尝试 `--fit`。SGLang 早期的 PR #29971 拿 llama.cpp 最慢的 `--cpu-moe` 做对比，高估了自己的收益，要避免这种情况；
8. 每格至少跑 2 次并报告波动。

**指标**：
- TTFT 和 TPOT/ITL 的 p50 / p99；
- 输出 tok/s、req/s；
- SLO 下的 goodput [DistServe]；
- 峰值显存和内存、冷启动和热启动的就绪时间；
- 精度（KL 散度和任务得分）。

## 7. 工程实现

### 7.1 技术路线与技术栈

**推荐路线：以 Mini-SGLang 为骨架改造。**

理由：
- MIT 许可，约 5k 行，出自 SGLang 团队；
- 已有 radix 缓存、分块 prefill、overlap 调度和 CUDA Graph，官方测试中与 SGLang 大致持平 [MiniSGLang]；
- G 模式能很快达到对手的水平，团队精力可以集中在 CPU 执行器、异构层和规划器这些真正的差异点上。

**备选路线**：
- 从零写，参考 nano-vllm：最自由，但要多花 1–2 个月才能追平；
- fork SGLang 本体：代码量大，而且很难为异构执行重构。

**技术栈**：

| 层 | 选型 |
|---|---|
| 运行环境 | Python 3.12（用 uv 管理）、PyTorch 2.x、CUDA 12.8+ 或 13（vLLM 0.33 已只支持 CUDA 13） |
| GPU 内核 | FlashInfer 0.7.x、sgl-kernel 或 vLLM 内核、Triton |
| 结构化输出 / 分词 | XGrammar、HF tokenizers |
| 服务与通信 | FastAPI + uvloop、pyzmq |
| CPU 执行器与自定义内核 | C++20 + CMake + scikit-build-core + nanobind；kt-kernel（pip）；ggml / ik_llama.cpp（submodule） |

**为什么是"Python 控制面 + C++/CUDA 数据面"**：
- 调研没有找到"编译型引擎核心胜过 overlap 做得好的 Python 核心"的直接证据，真正起作用的是工作放在哪里执行、能否重叠；
- Mini-SGLang 用 5k 行 Python 就与 SGLang 大致持平。

**v0.1 原型与上述路线的偏离**：
- 原型没有 fork Mini-SGLang，而是自研了一个设备无关的主干（设计上参考 Mini-SGLang 和 nano-vllm，均为 MIT 许可，没有拷贝代码）。
- 原因有两点：一是开发机没有 NVIDIA GPU，而 Mini-SGLang 只支持 GPU；二是本项目以 CPU 和异构执行为先，主干需要从一开始就不绑定设备。
- P1 在 GPU 机器上接入 FlashInfer 和 CUDA Graph 时，再评估是否移植 Mini-SGLang 的 GPU 组件。实现状态见 §7.5。

**代码量预算**：引擎本体约 1.5–2.5 万行 Python + 1–2 万行 C++/CUDA，不含第三方代码。

### 7.4 开发环境

- **本机不适合 GPU 开发**：本机是 i5-1240P、16 GB 内存、Iris Xe 核显、Windows 11，没有 NVIDIA GPU，也没有 C++ 编译工具链。
  - vLLM 和 SGLang 都不原生支持 Windows，本机跑不了它们，也做不了 GPU 开发。
- **本机能做的事**：
  - 当作远程开发客户端；
  - 在 WSL2 中开发 CPU 路径的小模型。这颗 CPU 只有 AVX2，没有 AVX-512 和 AMX，正好对应 S6 的"非 AMX"档。
- **需要另外准备的机器**：
  - GPU 开发和基准测试：Linux（Ubuntu 22.04/24.04）+ NVIDIA GPU；
  - S2 测试：大内存双路服务器（H2）。

## 9. 风险与对策

1. **对手迭代快**：vLLM 和 SGLang 大约每两周发一个版本；Paged Experts、DFlash 这类功能出现后很快就会变成默认。
   - 对策：P0 固定版本，之后每月重测；把优势建立在结构性设计上（三路径分配、规划器、CPU 内核带宽），而不是某一个内核上；每项差异化技术都做消融实验，证明各自的增益。
2. **对手补上 CPU 计算**：SGLang 的 Paged Experts 可能补上"用 CPU 计算缺失专家"，sglang-kt 也可能并回官方版本。
   - 对策：P2 结束时重新评估差距；如果差距被抹平，转向 S2/S3/S6 和部署体验（无需 fork、主机内存不足时支持磁盘层、原生 Windows）。
3. **硬件差异大**：AMX 只有 Xeon 第 4 代及以上才有，消费级 Intel 没有 AVX-512；sm_86/89/120 用不了 Hopper/Blackwell 数据中心卡的内核。
   - 对策：按 ISA 和计算能力（SM 架构）分派内核；性能目标按硬件档位分别设定。
4. **研究性风险**：消费级 megakernel 没有先例，MPK 的优势也有独立测量质疑。
   - 对策：S5 作为研究线，不进入主里程碑。
5. **精度风险**：Expert Deferral、FP4、近似注意力都会影响输出质量。
   - 对策：默认无损；有损开关必须同时报告精度；FP4 保留 FP8 兜底。
6. **工程规模**：
   - 对策：内核尽量以库形式复用；只自研调度、缓存、规划和异构编排这些"胶水"层；控制代码量。
7. **许可证**：
   - 对策：按 §7.2 管控；没有许可证文件的仓库只按论文重写。
8. **开发环境**：本机没有 NVIDIA GPU。
   - 对策：P0 之前先准备好 Linux GPU 机器；S2 需要大内存服务器。

## 10. 待确认事项

1. **目标硬件**：GPU 型号与显存；CPU 是 Xeon（有无 AMX）、EPYC 还是桌面平台；内存容量与通道数。
2. **目标模型**：稠密还是 MoE？具体是哪几个？
3. **优先场景**：建议先做 S1、S2、S3、S6，是否同意？S5（单用户延迟）是否需要进入主线？
4. **技术路线**：是否同意以 Mini-SGLang 为骨架？还是倾向从零开始？
5. **开源计划与许可证、团队规模、时间预期。**
