## 0. 摘要

**思路：用"专"换"快"。**

- vLLM 和 SGLang 要支持上百种模型和多种硬件。内核按通用的形状和启发式选择，热点路径要照顾所有模型。
- 只服务一个模型系列时，层数、维度、头数都是常量。融合方式、内核配置、CUDA Graph 档位和代价模型都可以按这一个模型、这一块卡来定（§3.2）。

**第一步：对齐。**

- 在选定模型和硬件上，吞吐、TTFT、TPOT 达到 vLLM / SGLang 中较好者的 0.95 倍以上，判据见 §1.2。
- 有可行路径：nano-vllm 用约 1.2k 行代码在 Qwen3-0.6B 上与 vLLM 吞吐相当 [nano-vllm]；Mini-SGLang 用约 5k 行在 Qwen3-32B 上与 SGLang 大致持平 [MiniSGLang]。两者用的都是与对手同源的内核。
- 对齐有两个用处：
  - 后续优化有可信的比较基线；
  - 对齐过程中逐算子剖析对手和自己，得到"哪些算子还有空间"的数据。

**第二步：场景优化。** 只在有证据表明还有空间的地方投入。

- **算子（A 场景）**：
  - 低 batch decode 和小模型受内核启动与小算子开销限制，按模型做的融合和持久化内核（megakernel）在这里有空间。MPK 在 batch 1–16 时每 token 延迟比 vLLM / SGLang 低 1.0–1.7 倍 [MPK]；Hazy 的 Llama-1B megakernel 比 SGLang 快 1.5 倍以上 [Hazy-Megakernel]。
  - 消费级卡（sm_86/89/120）用不了 Hopper / Blackwell 数据中心卡的新内核，对手的新优化多数到不了这些卡（§2.3）。
  - 大模型 BF16 的 decode 和 prefill 已接近带宽或算力上限，只要求对齐。
- **多级存储（B 场景）**：
  - 多轮对话、Agent、共享长文档这类负载，KV 的工作集远大于显存。在现有的 RTX 3090 服务器上估算：从主机内存载入 1K token 的 KV 约 12 ms，重算约 0.29 s（§4.4）。
  - 分层机制本身对手已有（SGLang HiCache、vLLM KV 卸载）。要超过它们，靠的是策略和协同：KVFlow 按 Agent 工作流淘汰和预取 KV，相对 SGLang 的分层缓存最高 2.19 倍 [KVFlow]；Cake 让载入和重算并行、在中间会合，TTFT 相对只重算或只载入平均降低 2.6 倍 [Cake]。
- **其他候选（P4）**：MoE 权重超出显存时的三路径专家执行（v0.2 的核心，v0.1 已有参考实现）；为目标模型训练专用草稿的投机解码。

**不做**：通用模型库、多卡 / 多机、纯 CPU 推理。

**预期收益**（定义见 §1，依据见 §5，P0 / P1 实测后修订）

| 阶段 / 场景 | 目标 | 置信度 |
|---|---|---|
| P1 对齐：Qwen3-0.6B、Qwen3-8B BF16，RTX 3090 | 测试矩阵中 ≥90% 的格子达到 vLLM / SGLang 较好者的 0.95 倍，且没有格子低于 0.85 倍 | 高（8B）/ 中（0.6B） |
| A1 小模型低 batch decode | batch 1–8 的 TPOT：Qwen3-0.6B 快 ≥1.2 倍（挑战目标 1.3 倍），Qwen3-1.7B 快 ≥1.05 倍 | 中 |
| A2 Qwen3-8B W4A16 低 batch decode | batch 1–8 的 TPOT 快 ≥1.05 倍（挑战目标 1.1 倍） | 中低 |
| B1 多轮对话 / Agent | KV 工作集为显存的 4.5 倍时：TTFT p50 比开启分层缓存的对手快 ≥1.2 倍，SLO 达标 ≥98% | 中低 |
| B2 共享长文档 | 0.1 req/s 时 TTFT p50 ≤1.96 s：比只用显存的对手快 ≥3 倍，比开启分层缓存的对手快 ≥1.15 倍 | 中低 |

**投入估计**：按 2 名熟悉 CUDA 和推理系统的工程师计，约 4 个月达到 P1–P3 的目标（含 P0 剩余的约 2 周，P2 与 P3 并行）。

## 1. 目标与边界

### 1.1 目标

- **模型**：只为选定的模型系列做快速路径。
  - 首个目标是 **Qwen3 稠密系列**。0.6B 到 32B 结构相同（GQA、QK-norm、RoPE、SwiGLU），只有尺寸和是否共享词嵌入不同。快速路径写一次，换尺寸只换常量和配置表。
  - 对齐和场景优化以 **Qwen3-8B** 为准（2026-11-11 已确认）。开发调试用 Qwen3-0.6B（服务器上已有），A1 另用 Qwen3-1.7B。
  - 第二个模型是 **Qwen3-30B-A3B**（MoE），P4 启用。
  - 选择理由：
    - v0.1 已实现 Qwen3 结构，并在 Qwen3-0.6B 真实权重上与 HF 逐 token 一致；
    - 8B 是单卡部署最常见的尺寸之一；
    - Qwen3-8B 的 BF16 权重约 16.4 GB，放进 24 GB 卡后只剩约 5 GB 给 KV。"KV 放不下"在这块卡上是真实问题，正好对应 B 场景。
  - 以后新增其他模型，按 §3.2 的"模型包"方式进行，控制面不变。
- **硬件**：
  - 主平台：现有服务器，RTX 3090 24 GB（sm_86）+ i7-10700K + 62 GB 内存 + PCIe 3.0。
  - 扩展平台：RTX 4090 / 5090（sm_89 / sm_120）；一块数据中心卡（A100 或 H100），用来确认对齐结论在对手最擅长的硬件上是否成立（P4）。
- **功能**：OpenAI 兼容 API（含流式）、连续批处理、分块 prefill、前缀缓存、CUDA Graph。结构化输出和投机解码放在 P4。
- **默认无损**：输出与参考实现（HF Transformers）在数值容差内一致。有损技术（FP8 KV、低比特权重、FP16 累加）必须显式开启，并报告精度。

### 1.2 "对齐"的可验证定义

**同条件**：同一块卡、同一份权重、同一精度、相同的 max_model_len 和显存占用比例（各引擎的 KV 容量随之确定，一并报告），使用同一个压测客户端（§6.4）。

**测试矩阵**（Qwen3-8B BF16，RTX 3090）：
- 输入 / 输出长度：1024 / 256（通用）、4096 / 256（prefill 为主）、256 / 1024（decode 为主），再加 ShareGPT 分布；
- 并发：1、2、4、8、16、32。
  - 每种长度只取"并发 × 单请求 token 数"不超过 KV 容量（取各引擎中最小的）的档位，避免抢占策略的差异干扰对比。
  - 按约 3.3 万 token 的容量估算（§4.4），1024 / 256 和 256 / 1024 测到并发 16，4096 / 256 测到并发 4。
- 离线吞吐：1,000 条 ShareGPT 请求。

**判据**：每个格子与 vLLM、SGLang 中较好的那个比较。
- 输出吞吐 ≥0.95 倍；
- TTFT、TPOT 的 p50 ≤1.05 倍，p99 ≤1.10 倍；
- ≥90% 的格子达标，且没有格子低于 0.85 倍，即视为对齐。

**顺序**：先在 Qwen3-0.6B 上过一遍（这个尺寸几乎全是调度和启动开销，检验运行时），再在 Qwen3-8B 上过（检验内核）。

### 1.3 场景优化的目标场景

| 场景 | 描述 | 主要指标 | 对手配置 |
|---|---|---|---|
| **A1** | 小模型（Qwen3-0.6B、1.7B）低 batch decode：交互式应用、小模型的服务化 | TPOT（batch 1、4、8） | vLLM / SGLang 各自的最佳配置 |
| **A2** | Qwen3-8B 量化（W4A16）低 batch decode：消费级卡上最常见的部署方式 | TPOT（batch 1、4、8）、TTFT | 同上，使用同一份量化权重 |
| **B1** | 多轮对话和 Agent：会话历史、工具调用循环反复复用同一前缀，工作集超出显存 | TTFT p50 / p99、SLO 下的吞吐、各级命中率 | 默认配置（只有显存前缀缓存）；开启分层缓存的最佳配置（SGLang HiCache；vLLM KV 卸载或 LMCache），主机内存和磁盘预算相同 |
| **B2** | 共享长文档：RAG、代码库问答，同一批文档被反复用作前缀 | 同上 | 同上 |

**非目标（v1 不做）**：
- 通用模型库：目标模型以外的结构只保留参考实现（用于测试），不做快速路径。
- 多卡 TP / EP / PP、多机部署、跨机 PD 分离。
- 纯 CPU 推理（v0.2 的 C 模式和 S6）。
- 非 NVIDIA 硬件。

## 2. 调研：对齐什么，哪里还有空间

### 2.1 对手的现状（2026 年 11 月）

| 能力 | vLLM 0.33.0（2026-11-02） | SGLang 0.5.23（2026-10-30） |
|---|---|---|
| 运行时 | V1 引擎。async scheduling 自 v0.14（2026-01）起默认开启。Model Runner V2 自 v0.29 起默认：请求状态常驻 GPU，Triton 构造输入，连同投机解码在内都不做 host 同步 [vLLM][vLLM-MRV2] | overlap（零开销）调度 [SGLang-v0.4]。Spec V2（投机解码与 overlap 结合）自 v0.5.11 起默认。分段 CUDA Graph 自 v0.5.10 起默认 [SGLang] |
| 前缀缓存 / KV 分层 | 哈希式自动前缀缓存（APC）；CPU / 磁盘 / 对象存储多级 KV 卸载；LMCache 等连接器 | RadixAttention；HiCache（GPU → 主机内存 → 存储三级）[HiCache] |
| 投机解码 | EAGLE / EAGLE-3、MTP、suffix、GPU n-gram、DFlash、P-EAGLE、DSpark。自适应验证目前只支持 DSpark，且只在 SM100 上可用 [DSpark] | EAGLE / EAGLE-3、MTP、DFlash、topk>1 的草稿树；n-gram 模式会关闭 overlap 调度 |
| 量化 | FP8、NVFP4 KV（SM8x/90/12x）、MXFP4、Marlin、Machete、QuTLASS；GGUF 已移出核心代码，改为插件 | FP8、AWQ / GPTQ（Marlin）、MXFP4 / NVFP4、W8A8 |
| 超显存权重 | `--cpu-offload-gb`；Weight Offloading V2（带预取）；都不在 CPU 上计算 [vLLM-CPU] | `--cpu-offload-gb`；Paged Experts（v0.5.23，可选），计算仍在 GPU 上 [SGLang-PE] |
| 低延迟 megakernel | 只覆盖个别模型和硬件（如 GB300 上的 DeepSeek-V4.1-Flash、AMD MI3xx 上的 `--monokernel`） | 可选插件，只覆盖 GB300 / MI350X 上的 DeepSeek-V4.1-Flash |
| 环境要求 | 0.33 只支持 CUDA 13，需要驱动 ≥580 | 0.5.23 的 wheel 要求 glibc ≥2.34，依赖 CUDA 13 |

**对齐要补齐的三件事**：
- **运行时**：两者都已做到 CPU 调度与 GPU 执行重叠，decode 用 CUDA Graph 消除启动开销。本项目 v0.1 两样都没有，这是 P1 的首要工作。
- **内核**：两者在 sm_86 上用的都是公开的内核库（FlashAttention-2 / FlashInfer、cuBLAS、Marlin、Triton），本项目直接复用同一批（§4.3）。
- **缓存**：显存前缀缓存两者都默认开启，分层缓存要显式开启。B 场景的对比两种配置都要测（§6.4）。

### 2.2 证据：对齐不需要大代码量，超越集中在开销占比高的地方

| 系统 | 出处 | 要点 |
|---|---|---|
| **nano-vllm** | MIT [nano-vllm] | 约 1.2k 行，仅离线推理。RTX 4070 Laptop 上跑 Qwen3-0.6B，吞吐与 vLLM 相当（vLLM 版本未注明） |
| **Mini-SGLang** | LMSYS 2025-12，MIT [MiniSGLang] | 约 5k 行 Python，包含 radix 缓存、分块 prefill、overlap 调度和 CUDA Graph。在 H200 上以 TP4 跑 Qwen3-32B，吞吐和 P90 TTFT/TBT 与 SGLang 大致持平 |
| **MPK** | OSDI'26 [MPK] | 把模型编译成单个持久化 megakernel。在 A100/H100/B200 上、batch 1–16 时，每 token 延迟比 vLLM/SGLang 低 1.0–1.7 倍。有一项独立测量显示它在部分 H100 测试格中不如 SGLang [ForgeMegakernel] |
| Hazy megakernel | Hazy Research 博客 2025-05 [Hazy-Megakernel] | Llama-1B 的低延迟 decode，相对 SGLang 超过 1.5 倍 |
| ForgeMegakernel | arXiv 2026 [ForgeMegakernel] | 相对 SGLang 0.5.18 的几何平均 1.21 倍 |

**运行时开销的分量**：
- vLLM v0.5.3 时，GPU 只有 38% 的时间在计算 [vLLM-perf24]。MRV2 在小模型上带来 +56% [vLLM-MRV2]，Spec V2 带来 +33% [SGLang-SpecV2]。
- 主机 CPU 核数不足会让 TTFT 恶化 1.47–7.11 倍 [HostCPU]；同机运行的其他进程可使吞吐下降 78.8% [CoLocation]。
- **对本项目的意义**：模型越小、batch 越小，运行时和启动开销的占比越大。这既是对齐的难点（0.6B），也是 A 场景的机会（§5.1）。

### 2.3 算子层面：消费级卡的机会

- **内核覆盖**：
  - FlashInfer 支持 SM75–SM121 [FlashInfer]；FA3 只支持 Hopper [FA3]；FA4 在 sm_120 上的路径退化为 SM80 风格 [FA4]。
  - sm_86/89/120 没有 WGMMA/TMEM，每个 block 的共享内存只有 99 KB，FA3、DeepGEMM、Machete、FlashMLA 都用不上。对手为数据中心卡做的新优化，多数到不了消费级卡。
  - 低延迟 megakernel 只覆盖个别数据中心卡上的个别模型（§2.1），调研时没有找到消费级卡上的公开实现。
- **消费级 Ampere 的算力特点** [GA102]：
  - RTX 3090 的 FP16 张量算力在 FP16 累加时为 142 TFLOPS；FP32 累加时只有一半，71 TFLOPS，而 BF16 只能用 FP32 累加。INT8 为 284 TOPS，是 BF16 的 4 倍。以上均为稠密算力。
  - 本项目在这块卡上实测 BF16 GEMM 为 62.8 TFLOPS（P0），约为标称值的 88%。
  - 所以在这块卡上，prefill 这类算力受限的部分有两条路：
    - INT8 W8A8；
    - "FP16 短累加 + 定期汇总到 FP32"：参考 DeepSeek-V3 在 FP8 GEMM 中每隔一段把张量核的部分和提升到 FP32 累加的做法 [DeepSeek-V3]。精度风险要实测。
- **只服务一个模型带来的便利**（以 Qwen3-8B 为例）：
  - GEMM 的 (N, K) 只有 5 种：QKV（4096 → 6144）、O（4096 → 4096）、gate_up（4096 → 24576）、down（12288 → 4096）、lm_head（4096 → 151936）。每种可以按 batch 档位离线调优。
  - attention 的头数比（32 : 8）和 head_dim（128）固定，decode 的 split-KV 切分可以按 3090 的 82 个 SM 定死。
  - QK-norm 是 Qwen3 的结构特点，可以和 RoPE、KV 写入融合成一个内核。
  - 每层的算子序列固定，可以整层甚至整个模型做成持久化内核。

### 2.4 多级存储：现状与研究

| 系统 | 出处 | 要点 |
|---|---|---|
| **HiCache** | SGLang [HiCache] | GPU → 主机内存 → 存储三级；主机侧用 page-first 布局，GPU 辅助的拷贝内核比 `cudaMemcpyAsync` 最多快 3 倍 |
| vLLM KV 卸载、LMCache | [vLLM]；[LMCache] | CPU / 磁盘 / 对象存储多级卸载，通过连接器接入 |
| CachedAttention | ATC'24 [CachedAttention] | 多轮对话的 KV 分层保存，按层预载 |
| **Pensieve** | EuroSys'25 [Pensieve] | GPU + CPU 两级缓存保存会话历史；扩展 PagedAttention，让多 token 输入可以跨非连续显存计算。吞吐是 vLLM 和 TensorRT-LLM 的 1.14–3.0 倍，但对比的是不做跨请求 KV 复用的 vLLM v0.2 和 TensorRT-LLM v0.9 |
| **Cake** | arXiv 2024 [Cake] | GPU 从前往后重算，I/O 从后往前载入，两者在中间会合。TTFT 相对只重算或只载入平均降低 2.6 倍；I/O 或算力严重受限时超过 10 倍 |
| **KVFlow** | NeurIPS'25 [KVFlow] | 用 Agent 工作流图估计每个 Agent 多少步后再次运行，据此淘汰和后台预取 KV。相对 SGLang 的分层 radix 缓存，大 prompt 的单个工作流最高 1.83 倍，多个并发工作流最高 2.19 倍。前提是工作流图静态已知，后续工作指出它不适合动态工作流 [PBKV] |

**结论**：
- 分层、按层预载、GPU 辅助拷贝这些机制，对手都已具备。本项目在这部分只求对齐。
- 空间在四个地方：
  1. 载入与重算的选择和拆分（Cake），用模型的精确代价常数驱动；
  2. 面向会话和 Agent 的保留与预取策略（KVFlow 一类）：对手的分层缓存不感知会话和工作流结构；
  3. 低带宽链路上的压缩：这台服务器的 PCIe 3.0 只有 12.9 GB/s；
  4. 调度与搬运协同：载入期间先跑别的请求，按层流水。

### 2.5 结论：做什么，不做什么

- **对齐有把握**：路径是"同源内核 + overlap 调度 + CUDA Graph"，已有小代码量的先例。主要风险是对手持续迭代（§9）。
- **A 场景（算子）**：空间集中在小模型和低 batch decode。Qwen3-8B BF16 的 decode 已接近带宽上限，不承诺超越。
- **B 场景（多级存储）**：相对对手的默认配置，收益大且确定；相对对手的分层缓存配置，收益来自策略、压缩和调度协同，证据中等。
- **不硬拼**：数据中心卡上的大 batch 吞吐，以及对手已经接近屋顶线的部分。

### 3.2 模型包：专用化的边界

- **通用部分**（与模型无关）：API 前端、调度器、KV 缓存与多级存储、搬运引擎、Model Runner 框架、压测与正确性工具。
- **专用部分**：每个模型系列一个"模型包"。

| 内容 | 说明 |
|---|---|
| 模型常量 | 层数、hidden、头数、KV 头数、head_dim、intermediate、词表、RoPE 参数。作为内核的编译期常量（C++ 模板参数或 Triton constexpr） |
| 权重变换 | 合并 QKV 和 gate_up；按目标内核重排（如 Marlin）；量化校准（AWQ / GPTQ / SmoothQuant）；FP8 KV 的缩放系数 |
| 融合计划 | 每层在 prefill、decode、混合 batch 下依次调用哪些（融合）内核，按 GPU 架构区分 |
| 内核配置表 | 每个 GEMM 和 attention 内核在各 batch 档位下的 tile / split 参数。由调优脚本在目标卡上生成，随模型包存放 |
| CUDA Graph 档位 | 捕获哪些 batch 大小，占多少显存 |
| 代价常数 | 每 token 的 FLOPs、权重字节、KV 字节，以及实测的各算子耗时。调度器（token 预算）、多级存储（载入还是重算）和投机解码（验证预算）共用 |
| 正确性基准 | 逐层与参考实现（v0.1 的 PyTorch 实现）和 HF Transformers 对比 |

- 新增一个模型 = 写一个模型包 + 在目标卡上跑一遍调优，控制面不动。
- 同一结构的不同尺寸（Qwen3-0.6B 到 32B）共享代码，只换常量和配置表。

### 3.3 进程与线程

- **API 进程**：HTTP/SSE、分词、chat template、增量反分词。
  - 与引擎进程分离，避免 GIL 争用拖慢调度循环。vLLM V1 和 SGLang 都这样拆分 [vLLM-V1][SGLang]。
  - 两个进程之间用 ZMQ 通信。
- **引擎进程的主循环**：
  - P1：overlap 调度，CPU 在 GPU 执行第 N 步时准备第 N+1 步，输出经旁路 stream 异步拷回 [SGLang-v0.4]；decode 用 CUDA Graph；采样在 GPU 上批量完成。
  - P1 之后视剖析结果，再把请求状态常驻 GPU、在 GPU 上构造输入（vLLM MRV2 的做法）[vLLM-MRV2]。
- **搬运**：L2 ↔ L1 用独立的 CUDA stream；L3 ↔ L2 用 I/O 线程。
- **CPU 核的划分**：控制面独占若干物理核，搬运和 I/O 线程另分 [HostCPU][CoLocation]。i7-10700K 只有 8 核，具体分配要实测。

### 3.4 一个 step 的时序（含多级存储）

```
CPU scheduler : [plan N+1]                     [plan N+2]                     ...
GPU compute   : [step N: L0 | L1 | ... | L35 | sample][step N+1: L0 | L1 | ...
L2 -> L1 copy :   [req R: KV of L0][KV of L1][KV of L2] ...         (copy stream)
NVMe -> L2    : [prefetch pages of queued requests] ...             (I/O threads)
```

- 前缀命中在 L2 / L3 的请求先进入"载入中"状态。调度器不等它，继续排其他请求。
- 载入按层进行：请求 R 第 i 层的 KV 到位后，它新 token 的第 i 层就可以算（层间流水）[HiCache][CachedAttention]。
- 链路慢、前缀又很长时，按代价模型把前缀拆成"重算段"和"载入段"并行进行 [Cake]（§4.4）。

### 4.1 API 前端

- OpenAI 兼容的 `/v1/completions` 和 `/v1/chat/completions`，支持 SSE 流式和 `usage`。

- 结构化输出（P4）用 XGrammar，语法在 API 进程里编译 [XGrammar]。

### 4.2 引擎主循环与调度器

- **沿用 v0.1**：
  - 连续批处理 [Orca]；
  - 带 token 预算（默认 2048）的分块 prefill；
  - KV 不够时先淘汰前缀缓存，再按重算方式抢占。
- **P1 改造**：
  - overlap 主循环（§3.3）；
  - batch 大小对齐 CUDA Graph 档位；
  - 批量构造输入（位置、slot mapping、FlashInfer 的 plan 参数），去掉逐请求的 Python 循环；
  - 采样在 GPU 上批量完成（v0.1 是逐请求采样）；
  - **默认调度改为 prefill 优先**（`prefill_first`，与 SGLang 默认相同）：有请求在等 prefill 时，这一步只做 prefill，不带 decode。v0.1 的 decode 优先（`decode_first`，Sarathi-Serve 的混合批）保留为选项。依据是 P1 对齐矩阵（P1 对齐报告）：
    - decode 优先时，8B 上同时到达的请求被拆进连续几步，每步还带着 decode，TTFT 有 4 格超限（达标率 79%）。实测 256 token 的 prefill 带上 1 个 decode 后，8B 上这一步多花约 24 ms（推测是 token 数从 256 变成 257，GEMM 多出一行 tile，未验证）。
    - 0.6B 上 decode 优先使 4096/256 并发 16、32 的 TPOT p50 超限（1.14、1.24 倍）。
    - 改为 prefill 优先后，8B 的 19 格全部达标。
  - **token 预算保持 2048**：试过 8192，同时到达的一批请求能并进更少的步，ShareGPT 并发 16 的 TPOT p99 明显下降；但输入长度相同、成批同时到达的负载里，前面的请求要等整批一起出首 token，8B 1024/256 并发 8 的 TTFT p50 升到 1.26 倍，所以没有采用。
  - **plan 参数必须已在 GPU 上**：FlashInfer 0.6 的 CUDA Graph decode wrapper 对 CPU 上的 `kv_indices` 用阻塞拷贝，等于每步一次流同步，主机要等 GPU 跑完上一步才能发下一步，overlap 实际失效（0.6B 单路每步 2575 µs、GPU 空闲 11.9%）。先把它异步拷到 GPU 再调 `plan()` 后，降到 2323 µs、空闲 2.1%。有回归测试守着：先在 GPU 上排一段空转，再跑一步，返回时 GPU 必须仍在忙。
- **P3 改造（多级存储感知）**：
  - 请求到达时查 radix 树：L1 命中直接排队；L2 / L3 命中先发起载入，进入"载入中"队列；
  - 载入完成后（按层流水时是第 0 层到位后）才进入可调度集合；
  - 抢占时优先把 KV 换出到 L2，而不是丢弃后重算。D2H 实测 13.2 GB/s，换出 1 GB 约 76 ms；H2D 与 D2H 同时进行时合计 22.6 GB/s（P0）。
- **前缀感知排序**：缓存压力大时，按最长前缀匹配（LPM）优先 [SGLang]。

### 4.4 KV 缓存与多级存储

**(a) 层级与容量**（Qwen3-8B BF16，RTX 3090 服务器，估算）

- 每 token 的 KV：2（K、V）× 36 层 × 8 个 KV 头 × 128 维 × 2 字节 = 144 KiB；FP8 时 72 KiB。

| 层级 | 介质 | 容量（BF16 KV） | 到上一级的带宽 |
|---|---|---|---|
| L1 | 显存：按 0.9 的显存占用比例，扣除权重 16.4 GB 和激活、CUDA Graph 等约 2 GB，剩约 4.8 GB | 约 3.3 万 token | — |
| L2 | 主机 pinned 内存：62 GB 中划出 32 GB | 约 21.7 万 token | PCIe 3.0，实测 12.9 GB/s |
| L3 | NVMe。这台服务器的系统盘是 SATA 机械硬盘，实测顺序读 148 MB/s，低于下面算出的盈亏点；机器上的 NVMe 是双系统里 Windows 的 NTFS 盘。L3 要另配 NVMe 或换机器测 | TB 级 | 盘的顺序读带宽，经 L2 再到 L1 |

**载入比重算快得多**（估算）：
- 载入 1K token 的 KV：151 MB ÷ 12.9 GB/s ≈ 12 ms。
- 重算 1K token：约 14 TFLOP（2 × 6.95B 非词嵌入参数 × 1,024，不含 attention）。按实测 GEMM 峰值 62.8 TFLOPS 的约 78% 计，约 0.29 s。
- 载入快约 25 倍；FP8 存放时约 50 倍。
- L3 与重算的盈亏点：盘的读带宽约 0.5 GB/s（BF16）。NVMe 普遍高于这个值，SATA SSD 在盈亏点附近。

**(b) 机制**（对齐 HiCache 已有的部分）

- radix 树的每个节点记录其页所在的层级（L1 / L2 / L3，可以同时在多级）。
- **写入策略**：
  - write-through：KV 生成后异步写到 L2，L1 淘汰时不用再拷；
  - 只对"可能复用"的前缀做 write-through（如会话历史、固定前缀），其余在淘汰时再写回。
- **布局**：
  - L1 沿用 layer-first（每层一个张量，FlashInfer 需要）；
  - L2 / L3 用 page-first（一页的所有层连续），便于整页 I/O；
  - 两种布局之间用 GPU 辅助的 gather / scatter 拷贝内核 [HiCache]。
- **按层流水载入**（§3.4）。
- **L3**：每页定长，`O_DIRECT` 读写，用 io_uring 异步提交。L3 到 L1 必须经过 L2，暂不考虑 GPUDirect Storage。

**(c) 差异化**

1. **载入 / 重算的决策与拆分** [Cake]：
   - 对每个命中段，用模型包的代价常数（每 token 的 FLOPs 和 KV 字节）和实测带宽，比较载入和重算。
   - 链路慢时（L3，或 PCIe 已被其他载入占满），按 Cake 的双向方式拆分：GPU 从头重算，I/O 从尾载入，在中间会合。
   - 估算拆分能省多少：设载入比重算快 r 倍，最优拆分比只载入省 1/(r+1)。
     - L2：r≈25，最多省约 4%，所以 L2 只做载入；
     - L3 用 3 GB/s 的 NVMe：r≈5.8，可省约 15%；
     - L3 用 SATA 盘：r≈1，接近省一半。
2. **会话与 Agent 感知的保留和预取**：
   - 多轮对话：用户读完回复再输入，间隔数秒到数分钟。会话在这段时间降到 L2，新一轮到达前按到达间隔的统计提前预取回 L1。
   - Agent：工具调用的耗时短且可预期。工具调用期间保留其 KV，或降到 L2 并在预计返回前预取。
   - 依据：KVFlow 用工作流图做同样的事，相对 SGLang 的分层缓存最高 2.19 倍 [KVFlow]。本项目不要求静态工作流图（它对动态工作流的局限见 [PBKV]），只用 API 提示参数（§4.1）和请求到达间隔的在线统计。
3. **压缩存放**：L2 / L3 可选 FP8 存放（有损，必须报告精度），PCIe 和磁盘流量减半、容量翻倍。无损压缩留作研究项。
4. **调度协同**：载入期间不阻塞 batch（§4.2）；按队列位置决定载入优先级；限制同时进行的载入数，避免 PCIe 拥塞。

**(d) 不做**：
- 非前缀的 KV 复用（例如 RAG 中文档顺序变化时拼接 KV）：属于近似方法，不在 v1 范围内。
- KV 留在主机内存、由 CPU 计算 attention：这台机器只有 8 核，CPU 读带宽约 27 GB/s，收益有限。

### 4.5 量化

- **P1 对齐以 BF16 为准**，排除量化格式差异的干扰。
- **P2 的两种格式**，都要先与对手对齐（使用同一份量化权重），再谈优化：
  - W4A16（AWQ / GPTQ 权重，Marlin 内核）[AWQ][GPTQ][Marlin]：消费级卡上最常见；
  - W8A8 INT8（SmoothQuant 类校准）[SmoothQuant]：用 sm_86 的 INT8 张量算力加速 prefill。
- **KV**：
  - BF16 默认；
  - FP8 可选，只用于存储、计算前反量化，用来扩大 L1 容量和压缩 L2 / L3；
  - INT4 KV [KIVI] 要定制 attention 内核，放在 P4 之后。
- **输入格式**：HF safetensors（BF16、AWQ、GPTQ、compressed-tensors）。GGUF 不在范围内。
- 任何量化配置都必须通过 §4.8 的精度回归。

### 4.6 投机解码（P4，可选）

- v0.1 已有 n-gram 草稿和投机采样验证，贪心模式下与普通解码一致 [SpecDec]。
- 只服务一个模型带来的机会：
  - 为目标模型和业务数据训练专用草稿（EAGLE-3 / DFlash）[EAGLE-3][DFlash]，接受率决定收益；
  - 验证预算按模型包的代价常数逐 step 选择 [DSpark]。
- 对比时双方用同一种草稿（§6.4）。

### 4.7 权重多级存储与 CPU-GPU 异构执行（P4）

- **场景**：MoE 权重超出显存。例如 Qwen3-30B-A3B 在 24 GB 卡上用 FP8 或 INT8（约 31 GB），而不是 INT4。
- **做法**：沿用 v0.2 的三路径专家执行。每个 step、每个专家在"GPU 常驻 / 换入 GPU / CPU 计算"三条路径中选择，让 PCIe 路径和 CPU 路径尽量同时结束 [KTransformers][SGLang-PE][AdaptiveExpert]。v0.1 已有参考实现（输出与 HF 一致）和放置规划器。
- **依据**：SGLang PR #42557 的官方实测（Qwen3-30B-A3B）[SGLang-PE]：
  - 16 GB 卡上，GPU 换入（Paged Experts）的单流 decode 为 205.6 tok/s，高于调优后的 llama.cpp（194.4）；
  - 8 GB 卡、并发 4 时，在 CPU 上算缺失专家的 llama.cpp 达到 41 tok/s，Paged Experts 只有 11–12；
  - 两种方式各有胜负，逐 step 选择的系统有机会每一格都取较好者。
- **这台服务器上**：CPU 有效读带宽约 27 GB/s，PCIe 约 12.9 GB/s，比值约 2.1（P0）。缺失专家在 CPU 上算，约比换入快 2 倍。CPU 只有 8 核、仅 AVX2，P4 需要 C++ 内核（复用 kt-kernel / ggml）。
- **P4 之前冻结**：不改 `hybrid/` 和 `planner/` 的逻辑，只保持测试通过。`planner/` 的硬件画像（PCIe、DRAM 带宽实测）复用到多级存储的代价模型。

### 4.8 可观测性与正确性

- **可观测性**：
  - Prometheus 指标；NVTX 区间；
  - 每个 step 的 GPU 时间线和搬运时间线（L1 / L2 / L3）导出为 Chrome trace；
  - 各级命中率，以及载入 / 重算的决策记录。
- **正确性测试**：
  - 逐层激活与参考实现、HF Transformers 对比（BF16 下余弦相似度 >0.999）；
  - 固定 prompt 集上的贪心输出一致；
  - 相对 BF16 参考的 KL 散度或 logprob 差；
  - lm-eval-harness 上的 GSM8K / MMLU 与参考相差在 ±0.5 分以内；
  - 多级存储：无损模式下，从 L2 / L3 载入的 KV 与原 KV 逐字节一致；经过分层后续写的输出，与不经分层时一致；
  - 每个融合内核都有单元测试，与未融合的参考实现对比。
- **有损开关**（FP8 KV、低比特权重、FP16 累加）开启时必须同时报告精度。

## 5. 性能目标与依据

### 5.1 屋顶线估算（RTX 3090）

- 显存带宽用 P0 实测的拷贝带宽 788 GB/s（读写合计，约为标称 936 GB/s 的 84%）。decode 以读为主，实际可达带宽可能略高，所以这里的下限偏保守。
- 启动开销按每层约 11 个内核、每个内核 1.5–3 µs（CUDA Graph 内）估算。

| 配置 | 每 token 读的权重 | 数据搬运下限 | 对应速度上限 | 启动开销 / 搬运时间 |
|---|---|---|---|---|
| Qwen3-0.6B BF16，batch 1 | 约 1.19 GB（含共享的词嵌入 0.31 GB） | 约 1.5 ms | 约 660 tok/s | 约 30–60% |
| Qwen3-1.7B BF16，batch 1 | 约 3.44 GB | 约 4.4 ms | 约 230 tok/s | 约 10–20% |
| Qwen3-8B W4A16，batch 1 | 约 4.8 GB（量化部分约 3.6 GB + BF16 lm_head 1.24 GB） | 约 6.1 ms | 约 163 tok/s | 约 10–20% |
| Qwen3-8B BF16，batch 1 | 约 15.1 GB | 约 19 ms | 约 52 tok/s | 约 3–6% |

- 结论：
  - 0.6B 上启动开销与数据搬运同一量级，持久化内核的空间最大，对应 A1；
  - 1.7B 和 8B W4A16 上启动开销占一到两成，融合和形状专用 GEMV 能拿回一部分，对应 A1、A2；
  - 8B BF16 已由带宽决定，只要求对齐。
- P0 实测：
  - v0.1 在 0.6B 上单路每 token 27 ms，只用到带宽的约 6%。P1 先要把这部分差距补上。
  - 对手（过渡版本）在 8B BF16 上单路每 token 20.1–20.2 ms，约合 750 GB/s，达到上表下限的约 95%。
  - 对手在 0.6B 上：SGLang 2.34 ms，vLLM 2.59 ms，比下限多 0.8–1.1 ms，这部分是每步的固定开销（P0 基线报告 §3、§4）。

### 5.2 目标

| 阶段 / 场景 | 目标（同硬件、同精度、版本固定） | 依据 | 置信度 |
|---|---|---|---|
| **P1 对齐** | Qwen3-0.6B、Qwen3-8B BF16 通过 §1.2 的判据（2026-11-12 已达成，见 P1 对齐报告） | nano-vllm、Mini-SGLang 以小代码量达到对手水平 [nano-vllm][MiniSGLang]；内核同源 | 高（8B）/ 中（0.6B：运行时开销占比大，主循环必须做到与对手同一水平） |
| **A1** 小模型低 batch decode | batch 1–8 的 TPOT：Qwen3-0.6B 快 ≥1.2 倍，挑战目标 1.3 倍（靠持久化内核）；Qwen3-1.7B 快 ≥1.05 倍 | P0 实测（P0 基线报告 §6）：对手最好的配置是 SGLang + torch.compile，单路 0.6B 2.14 ms、1.7B 4.76 ms；1.7B 只比按 788 GB/s 算的带宽下限慢 8%，原定的 1.15 倍要读到标称带宽的约 90%；0.6B 按剖析分解，常规优化约能到 1.75 ms（快约 1.22 倍）。§5.1 的开销占比；MPK 1.0–1.7 倍、Hazy 超过 1.5 倍（Llama-1B）、ForgeMegakernel 1.21 倍 [MPK][Hazy-Megakernel][ForgeMegakernel] | 中（消费级卡上的 megakernel 没有先例；MPK 的优势有独立测量质疑） |
| **A2** 8B 量化低 batch decode | W4A16，batch 1–8 的 TPOT 快 ≥1.05 倍，挑战目标 1.1 倍 | P0 实测（P0 基线报告 §6）：对手都用 Marlin 内核，单路最好 7.22 ms，是带宽下限的 1.17 倍；快 1.1 倍要求整体读带宽达到拷贝带宽的 94%。§5.1：启动和小算子约占一到两成；融合与形状专用 GEMV | 中低 |
| 8B BF16 decode、prefill | 只要求对齐 | 受带宽或算力限制，对手已接近屋顶线 | — |
| **B1** 多轮 / Agent | 多轮对话 192 会话（KV 工作集为显存 KV 的 4.5 倍，主机内存 30 GB）时：TTFT p50 比开启分层缓存的对手（主机内存预算相同）快 ≥1.2 倍（对 SGLang HiCache 即 ≤130 ms）；SLO（TTFT ≤2 s、TPOT ≤100 ms）达标 ≥98%（对手 96%） | P0 实测（P0 基线报告 §7）：对手的分层缓存已比只用显存的默认配置快 1.6–2.8 倍，命中率达到理想的 90%–98%，原定的"比默认配置快 ≥3 倍"区分不出好坏；余量在载入速度和尾延迟（p99 约 4 s）。§4.4：载入比重算快约 25 倍；Pensieve 1.14–3.0 倍（对不做跨请求复用的基线）[Pensieve]；KVFlow 对 SGLang 分层缓存最高 1.83–2.19 倍 [KVFlow] | 中低 |
| **B2** 共享长文档 | 0.1 req/s（P0 的 0.3 req/s 两家都过载）时：TTFT p50 比只用显存的对手快 ≥3 倍、比开启分层缓存的对手（主机内存预算相同）快 ≥1.15 倍，对 SGLang 即 ≤1.96 s（它只用显存 5.89 s，加主机层 2.82 s） | P0 实测（P0 基线报告 §7）：分层缓存只比只用显存快 1.7–2.1 倍，命中率 57%–58%（理想 80%），"快 ≥3 倍"仍有区分度；余量在按访问频率保留文档、载入速度、命中请求不被长 prefill 挡住。同上；Cake 平均 2.6 倍（对只重算或只载入）[Cake]；§4.4 估算 L3 拆分可省约 15% | 中低 |

**实施优先级**：P1 对齐是一切的前提。P2（算子）和 P3（多级存储）互不依赖，可以两人并行。A1 的持久化内核作为研究线，不阻塞主里程碑。

### 6.3 模型与负载

**模型**：
- Qwen3-0.6B、Qwen3-1.7B（P1、A1）；
- Qwen3-8B：BF16、AWQ W4A16、W8A8 INT8。对手与本项目使用同一份量化权重；
- Qwen3-30B-A3B（P4）。

**负载**：
- 对齐矩阵：见 §1.2。
- A 场景：batch 1、4、8 的 decode（输入 512、输出 512、忽略 EOS）；4K prompt 的 TTFT。
- B 场景：
  - **多轮对话**：取 ShareGPT 中 ≥4 轮的对话，按"用户思考时间"（例如均值 30 s 的指数分布）回放。会话数一直扫描到工作集是 L1 容量的 2–20 倍；
  - **Agent**：多步工具调用轨迹，每一步是"一次生成 + 一段工具耗时 + 结果追加到上下文"，工具耗时按分布采样。有公开轨迹时优先用公开轨迹；
  - **共享长文档**：一组 8K–24K token 的文档，请求按 Zipf 分布选文档，再附一个短问题；
  - 每类负载都报告"理想复用率"（缓存无限大时的命中率），作为解读结果的背景；
  - 另测一组没有复用的负载，确认多级存储的额外开销（如 write-through 拷贝）不拖慢普通请求。

### 6.4 工具与公平性

**客户端**：
- 所有引擎统一用同一个压测客户端（`benchmarks/bench_serving.py`），或参数相同的 `vllm bench serve` / AIPerf，并以多进程模式运行。单进程 asyncio 客户端在高负载下会抬高测得的 TTFT 和 TPOT [BenchBias][AIPerf]。
- 再用各引擎自带的工具交叉验证一次。

**工具默认值的坑**：
- `vllm bench serve` 默认不预热，也不忽略 EOS；
- `sglang bench_serving` 默认预热 1 次，并且忽略 EOS（除非加 `--disable-ignore-eos`）。

**公平性规则**：
1. 使用相同的权重；量化时使用同一份量化权重；
2. KV dtype、max_model_len、显存占用比例、最大并发保持一致，并报告各引擎的 KV token 容量；
3. 分块大小要么统一，要么报告各引擎调到最佳后的值；
4. 对齐矩阵和 A 场景关闭前缀缓存，或在每轮之间清空；
5. B 场景中，对手的默认配置和开启分层缓存的最佳配置都要测，主机内存和磁盘预算与本项目相同；
6. chat template 和采样参数保持一致；
7. 投机解码要么全部关闭，要么全部开启并使用同一种草稿，同时报告接受率；
8. 每个基线都调到最佳（CUDA Graph 档位、分块大小、调度策略等），并记录所用参数；
9. 每格至少跑 3 次，报告中位数和波动。

**指标**：
- TTFT 和 TPOT / ITL 的 p50 / p99；输出 tok/s、req/s；SLO 下的 goodput [DistServe]；
- 峰值显存和内存；冷启动和热启动的就绪时间；
- B 场景：各级命中率、载入量、重算量、PCIe 和磁盘的利用率；
- 精度：KL 散度和任务得分。

## 7. 工程实现

### 7.1 技术路线与技术栈

**路线：在 v0.1 原型的主干上改造，不 fork Mini-SGLang 或 SGLang。**

理由：
- v0.1 的调度器、分页 KV、radix 缓存和参考模型都已与 HF 对齐，有 37 项测试保护；分页 KV 的布局已与 FlashInfer 兼容。
- 缺的是 GPU 快速路径（FlashInfer、CUDA Graph、融合算子）和运行时（overlap、进程拆分）。这两部分参考 Mini-SGLang 和 nano-vllm 的做法补上，两者都是 MIT 许可。

**备选**：把 Mini-SGLang 的 GPU 组件直接移植过来（MIT，可以引入代码）。P1 进度落后时再评估。

**技术栈**：

| 层 | 选型 |
|---|---|
| 运行环境 | Python 3.12（用 uv 管理）、PyTorch 2.x、CUDA 12.x 或 13（取决于服务器驱动，§6.1） |
| GPU 内核 | FlashInfer（attention、采样、小算子）；cuBLASLt；Marlin 与 CUTLASS（经 vLLM 或 sgl-kernel 的预编译算子）；Triton（调优和快速原型）；自研 CUDA C++（融合内核、持久化内核、搬运内核） |
| 构建 | 自研 CUDA 内核用 PyTorch C++ 扩展，或 scikit-build-core + nanobind。服务器上已有 CUDA 12.4 工具链（`/usr/local/cuda-12.4`，未加入 PATH） |
| 服务与通信 | FastAPI + uvloop、pyzmq |
| 多级存储 | pinned 内存池（`cudaHostAlloc`）；L3 用 io_uring（liburing），或线程池 + `O_DIRECT` |

**为什么是"Python 控制面 + C++/CUDA 数据面"**：
- 调研没有找到"编译型引擎核心胜过 overlap 做得好的 Python 核心"的直接证据。真正起作用的是工作放在哪里执行、能否重叠；
- Mini-SGLang 用 5k 行 Python 就与 SGLang 大致持平。

### 7.3 目录结构（规划）

```
python/tandem/
  entrypoints/      # OpenAI 兼容服务、CLI（API 进程）
  engine/           # overlap 主循环、进程间通信
  scheduler/        # 连续批处理、分块 prefill、载入感知的调度
  cache/            # 分页 KV、radix 树
    tiered/         # L2 主机内存池、L3 NVMe、搬运引擎、保留与预取策略
  executor/         # Model Runner、CUDA Graph 管理、批量采样
  models/           # 参考实现：Llama / Qwen2 / Qwen3 / Qwen3-MoE（正确性基准）
  packs/
    qwen3/          # Qwen3 稠密模型包：快速路径、权重合并与重排、融合计划、配置表、代价常数
  kernels/          # 内核的 Python 封装：FlashInfer、Marlin、Triton、自研
  planner/          # 硬件画像、代价模型（多级存储复用）
  hybrid/           # 三路径专家执行（冻结至 P4）
  spec/             # 投机解码（P4）
csrc/cuda/          # 自研内核：融合算子、小 M GEMV、持久化 decode、布局转换与搬运
benchmarks/         # 对齐矩阵、A / B 场景负载、结果归档
tests/              # 数值对齐、内核单测、端到端、精度回归
docs/
```

**代码量预算**：引擎本体约 0.8–1.2 万行 Python + 0.5–1 万行 CUDA C++，不含第三方代码。v0.1 目前约 3k 行 Python。

### 7.4 开发环境

- **本机**：i5-1240P、16 GB 内存、Iris Xe 核显、Windows 11，没有 NVIDIA GPU。只用来编辑代码，以及在 CPU 上跑正确性测试（参考实现与 HF 的对齐测试不需要 GPU）。
- **GPU 开发与对比**：RTX 3090 服务器。跑最新版对手要先满足 §6.1 的环境前置条件。编译自研内核用服务器上已有的 CUDA 12.4 工具链（`/usr/local/cuda-12.4`，需加入 PATH）。
- **服务器上现场编译（JIT）的两个坑**（P0 实测，tandem 在 P1 接 FlashInfer 时同样会遇到）：
  - PATH 里默认的 C/C++ 编译器是 `/usr/local/gcc-11.2`，但它的 libstdc++ 不在运行时链接器的搜索路径里。用它编译的 C++ 扩展（FlashInfer 的 JIT 内核、PyTorch C++ 扩展）加载时会报 `GLIBCXX_3.4.29 not found`。运行时加 `LD_LIBRARY_PATH=/usr/local/gcc-11.2/lib64`，或改用系统的 `g++-9` 编译。
  - 系统 nvcc 是 12.4。FlashInfer 0.7 编译时会加 `--compress-mode=size`（CUDA 12.8 才有），在这台机器上现场编译会失败；0.6.7 可以。P1 接 FlashInfer 时，要么固定在能用 nvcc 12.4 编译的版本，要么用预编译的 `flashinfer-jit-cache`，要么在用户目录另装一套 CUDA ≥12.8 的 nvcc（pip 的 `nvidia-cuda-nvcc-cu12` 里只有 `ptxas`）。
- **模型传输**：服务器不能联网，经 VPN 只有约 1.3 MB/s。Qwen3-8B BF16（16.4 GB）把 BF16 的高低字节拆开压缩后，线上约为原始体积的 72%，实际传了约 3 小时。建议解决联网，或用移动硬盘拷贝（P0 基线报告 §9）。

## 9. 风险与对策

1. **对齐的目标在移动**：vLLM 和 SGLang 大约每两周发一个版本。
   - 对策：P0 固定版本，之后每月重测最新版并记录差距。P1 的退出判据以固定版本为准，最新版的差距单独报告。
2. **环境装不了最新版的对手**：驱动 550、glibc 2.31。
   - 对策：P0 先解决（§6.1）；解决不了就用云上同代的卡做对比。
3. **专用化的覆盖面窄**：只服务一个模型系列。
   - 对策：模型包把专用部分限定在一个目录里；同结构的不同尺寸共享代码；新增模型的实际成本在 P4 用 Qwen3-30B-A3B 实测。
4. **算子优化的空间可能比估算小**：对手在新版本里也会补融合和图优化。
   - 对策：先剖析再选题；8B BF16 decode 和 prefill 不承诺超越；持久化内核作为研究线，不阻塞里程碑。
5. **多级存储的收益依赖负载**：没有复用的负载上没有收益，还多了拷贝开销。
   - 对策：公开负载定义和理想复用率；单独测无复用负载，要求不退化；write-through 只对可能复用的前缀开启。
6. **低带宽链路**：这台服务器是 PCIe 3.0（12.9 GB/s），磁盘型号未知。
   - 对策：结论按硬件档位分别报告；在 PCIe 4.0 / 5.0 的机器上复测（H2）。
7. **精度风险**：FP8 KV、低比特权重、FP16 累加都会影响输出。
   - 对策：默认无损；有损开关必须同时报告精度。
8. **自研 CUDA 内核的工程量和维护成本**。
   - 对策：先用库内核对齐，只在剖析表证明值得的地方自研；每个内核都有单元测试。
9. **许可证**：
   - 对策：按 §7.2 管控；没有许可证文件的仓库只按论文重写。

## 10. 已确认与待确认事项

**已确认**：
- 2026-11-11：首个目标模型定为 **Qwen3-8B**。P1 对齐、A2 和 B 场景都以它为准。
- 2026-11-11：P0 先不动服务器系统，用当前环境能装的旧版对手过渡（vLLM 0.32.0+cu129、SGLang 0.5.10，§6.1 选项 3）。这批数据只作开发参考，不作为对齐结论。
- 2026-11-12：P1 对齐判定达标（8B 19/19 格，0.6B 24/25 格）。0.6B ShareGPT 并发 32 的 TPOT p99 记为突发请求顺序造成的统计波动，不再为它改引擎或评测方法（P1 对齐报告 §4）。
- 2026-11-13：按 P0 实测修订 §5.2 的目标：A1 0.6B ≥1.2 倍（挑战 1.3 倍）、1.7B ≥1.05 倍；A2 ≥1.05 倍（挑战 1.1 倍）；B1 改为对同预算分层缓存快 ≥1.2 倍且 SLO 达标 ≥98%；B2 补测 0.1 req/s 后，沿用原口径（比只用显存快 ≥3 倍、比分层缓存快 ≥1.15 倍），即 TTFT p50 ≤1.96 s。P0 至此完成。

1. **第二个模型**：默认 Qwen3-30B-A3B（P4 启用），P4 开始前确认即可。
2. **目标硬件**：以现有 RTX 3090 为主平台是否合适？是否需要在数据中心卡上也对齐？
3. **对齐用的环境**：P1 验收前，要么把服务器驱动升级到 ≥580（SGLang 0.5.23 还需要 Docker 或 glibc ≥2.34 的系统），要么租云上同代的卡。走哪条路？
4. **场景优先级**：先做 A（算子：低 batch decode）和 B（多级存储：多轮对话、Agent、共享长文档），是否同意？业务上是否有更重要的场景？
