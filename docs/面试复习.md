## 0. 先背熟的三段话

**一句话**：我从零写了一个面向 Qwen3 的大模型推理引擎 tandem，在同一张 RTX 3090 上和 vLLM、SGLang 对齐，并在小模型低并发场景下超过了它们。

**30 秒版**：
- tandem 是一个 OpenAI 兼容的推理服务，结构上对标 vLLM / SGLang：连续批处理、分页 KV 缓存、前缀缓存、CUDA Graph、overlap 调度、API 和引擎分进程。
- 我先在同一台机器上把 vLLM 和 SGLang 的性能测成基线，再按一套固定的判据做对齐：Qwen3-8B 的 19 个测试格全部达标，0.6B 的 25 格达标 24 格。
- 之后针对小 batch decode 自己写了 Triton 内核（GEMV、decode attention），0.6B 低并发时比"开了 torch.compile 的 SGLang"快 4%–8%。
- 还支持了 4 bit AWQ 量化模型：用 CUDA C++ 写了 W4A16 内核，权重直接读进 tensor core 的 MMA 片段，8B AWQ 在 batch 1/4/8 时 decode 比对手快 9%/7%/5%，和 vLLM 逐 token 输出一致。

**2 分钟版**：在 30 秒版的基础上，挑一个"定位问题"的故事讲细：
- 首选第 3.3 节"每步一次的隐藏同步"：nsys 发现 → 读 FlashInfer 源码确认 → 一行修复 → 单路 decode 快 10%，并补了回归测试。
- 备选第 3.5 节"p99 抽签"：怎么判断一个不达标的格子是统计噪声而不是性能问题。

## 1. 项目全景

### 1.1 架构（面试时可以边画边讲）

```
客户端 ──HTTP──> API 进程（FastAPI）：分词、增量反分词、停止串、流式返回
                     │  multiprocessing Pipe
                     ▼
               引擎核心进程：调度器 → ModelRunner → GPU
                 · 调度：连续批处理，prefill 优先，token 预算 2048，KV 不够时抢占重算
                 · KV：分页（每页 16 token）+ radix 树前缀缓存（LRU、路径加锁）
                 · 执行：decode 走 CUDA Graph（按 batch 分档），prefill 走 eager
                 · overlap：GPU 跑第 N 步时，CPU 已经在准备第 N+1 步
```

- **为什么分两个进程**：Python 有 GIL。同一进程里，HTTP 流式返回的协程和引擎线程抢 GIL，引擎最多可能等一个切换间隔（5 ms）才能发下一步，比 0.6B 一整步 decode（约 2 ms）还长。证据：`python/tandem/engine/mp_engine.py` 开头的说明。

### 1.2 阶段与结果

| 阶段 | 内容 | 结果 | 证据 |
|---|---|---|---|
| v0.1 | 参考实现：调度、分页 KV、前缀缓存、模型、OpenAI 接口；PyTorch 实现 | 正确性对齐 HF（float64 下 logits 误差 1e-8 以内）；GPU 上 0.6B 单路 27 ms/token，只有最强对手的 0.06–0.12 | P0 基线报告 §2.1、§3.4 |
| P0 | 同机测 vLLM / SGLang 的基线：对齐矩阵、A/B 场景、nsys 逐算子剖析 | 见第 2、4 节 | `docs/P0基线报告.md` |
| P1 | GPU 快速路径，和对手对齐 | 8B 19/19 格达标，0.6B 24/25 格 | `docs/P1对齐报告.md` |
| P2（进行中） | 自写内核，小模型低并发超过对手 | A1：0.6B 快 4%–8%，1.7B 快 1%–4%；A2（8B AWQ）：batch 1/4/8 快 9.2%/6.9%/4.8% | 第 3.6–3.9 节 |

## 2. 评测方法（面试必问："你怎么证明比 vLLM 快？"）

### 2.1 对齐判据（设计方案 §1.2）

- **矩阵**：输入/输出 1024/256、4096/256、256/1024，加 ShareGPT 真实分布；并发 1、2、4、8、16、32；另加 1000 条请求的离线吞吐。
- **每格的比较对象**：吞吐更高的那个对手（vLLM 或 SGLang），只比一家，不取各指标的最好值拼起来。
- **标准**：吞吐 ≥0.95 倍；TTFT、TPOT 的 p50 ≤1.05 倍，p99 ≤1.10 倍；≥90% 的格子达标，且没有格子吞吐低于 0.85 倍。

### 2.2 公平性措施（被问"会不会不公平"时逐条说）

- **同一台机器、同一个压测客户端**（`benchmarks/bench_serving.py`），客户端和服务端同机，排除网络。
- **KV 容量对齐**：8B 上三家都固定在 32,992 token。vLLM 用 `--kv-cache-memory-bytes`，SGLang 用 `--max-total-tokens`，tandem 用 `--kv-cache-gb`。否则 KV 大的一方在高并发时少抢占，比较就不公平。
- **对手调到最佳**：例如 SGLang 在 24 GB 卡上默认只把 CUDA graph 捕获到 batch 24，并发 32 时退回逐个启动内核，0.6B 的吞吐只剩 0.61–0.78。我们给它加了 `--cuda-graph-max-bs 64`，否则结论会反过来（P0 基线报告 §3.3）。A 场景的对手还另测了 SGLang + torch.compile。
- **重复与配对**：每格跑 3 次，每次换一组提示词，取中位数；ShareGPT 按提示词组配对比较。
- **版本固定**：所有结果都记录引擎版本、启动参数和环境变量。

### 2.3 剖析方法

- 用 Nsight Systems 抓稳态 decode，按"每步"平均各类内核的时间，同时统计 GPU 空闲占比（`benchmarks/profile_engine.py`）。
- **坑**：vLLM 0.32 的 EngineCore 里，`cudaProfilerStart` 触发不了 nsys 采集，改为 `nsys launch` 启动服务，再从外部 `nsys start` / `nsys stop`。

### 2.4 统计上的坑：p99 不一定可信

- 每档请求数是 max(8, 4×并发)，并发 32 时 128 个请求，p99 实际就是第二差的那一个，波动非常大。
- 遇到不达标的格子，先确认是性能问题还是统计噪声，具体见第 3.5 节。

## 3. 关键优化（按时间顺序）

每条按"问题 → 怎么发现 → 做法 → 效果 → 为什么这样取舍 → 证据 → 可能的追问"整理。

### 3.1 P1 的 GPU 快速路径（对齐的基础）

- **问题**：v0.1 单路 27 ms/token，SGLang 是 2.34 ms，差一个数量级。主要有两个原因：
  - 每步的固定开销太大：每个算子单独启动内核，还有 Python 调度开销；
  - 参考实现的 attention 每步都把整段 K/V 补齐成稠密张量。
- **做法**：
  - **attention**：换成 FlashInfer 分页 attention。prefill 和混合步用 prefill wrapper，decode 用 decode wrapper；GQA ≥4（8B）时用 tensor core 版的 decode 内核，和 SGLang 的选择一样。
  - **小算子**：RMSNorm、残差加 RMSNorm、SiLU×up、RoPE 都换成 FlashInfer 的内核。
  - **QK 前处理融合**：用 Triton 写了 QK-norm + RoPE + 写 KV 的融合内核，一次启动代替原来的 7 次（`python/tandem/layers/triton_ops.py`）。
  - **合并投影**：q/k/v 合成一个 qkv_proj，gate/up 合成 gate_up_proj，每层少两次 GEMM；残差在层间传递，"加残差 + norm"合成一个内核。
  - **CUDA Graph**：decode 按 batch 分档捕获（1、2、4、8、16、24…64）。batch 凑不满一档时，多出的空行把 KV 写到一个专门留出来、永远不分配给请求的空闲块里，不会污染真实请求（`python/tandem/executor/cuda_graph.py`）。
  - **overlap 调度**：第 N 步采样出的 token 先留一个占位符，下一步的输入直接在 GPU 上从上一步的输出里取（gather），主机不用等。采样结果拷到双缓冲的 pinned 内存，用 CUDA event 通知。主机只在需要处理上一步结果时等一次。
  - **采样**：在 GPU 上批量完成，不做任何同步。
  - **进程拆分**：API 进程和引擎核心进程分开；增量反分词放在 API 进程。
- **效果**：P1 对齐（见 3.2–3.5）；0.6B 单路从 27 ms 降到约 2.2 ms，约 12 倍。
- **证据**：提交 `4868bbf`；`docs/P1对齐报告.md` §5。
- **可能的追问**：
  - *CUDA Graph 怎么处理 batch 变化？* 按档捕获，向上取整到最近一档，多出的行写到空闲块。
  - *overlap 怎么保证正确？* 第 N 步的输入里有一个 token 还没算出来，就在 GPU 上从第 N-1 步的输出张量里按行号取，而不是从主机传；请求在主机上的状态晚一步更新。有测试检查 overlap 和同步执行的输出逐 token 一致（`tests/test_overlap.py`）。

### 3.2 调度策略：decode 优先 → prefill 优先

- **问题**：P1 第一次跑 8B 矩阵，吞吐都达标了，但 TTFT 有 4 格超限，只有 79% 的格子达标。
- **怎么发现**：做了 TTFT 实验，单独改一个变量看效果（关 overlap、开 prefill 优先、改用线程模式），再看每个请求的到达和首 token 时间。
  - 原因是两个请求几乎同时到达时，第二个总会被排到下一步，而那一步还带着第一个请求的 decode。
  - 还看到混合步比纯 prefill 慢很多：256 token 的 prefill 带上 1 个 decode 后，一步多花约 24 ms。推测是 token 数从 256 变成 257，GEMM 多出一行 tile，没有验证。
- **做法**：默认改成 prefill 优先（和 SGLang 默认一样）：有请求等 prefill 时，这一步只做 prefill，不带 decode。Sarathi 式的 decode 优先保留为选项。
- **效果**：8B 的 19 格全部达标。0.6B 上 decode 优先原本还让 4096/256 并发 16、32 的 TPOT p50 超限（1.14、1.24），这个问题也一起解决了。
- **取舍**：prefill 优先会让正在 decode 的请求在 prefill 时停顿，TPOT 尾部可能变差；但对手也是这么做的，实测 TPOT 都在判据以内。
- **证据**：提交 `480e102`；P1 对齐报告 §6.1；设计方案 §4.2；`tests/test_scheduler.py` 里两种策略各有测试。

### 3.3 一行修复：FlashInfer plan() 每步一次的隐藏同步（最好讲的故事）

- **问题**：0.6B 单路 decode 每步 2575 µs，比 SGLang 的 2419 µs 慢；GPU 空闲 11.9%，说明是 CPU 在拖后腿。
- **怎么发现**：
  1. 先加了按环节计时的开关 `TANDEM_STEP_TIMING`，但只能看到时间都耗在"等 GPU"上。
  2. 再看 nsys 的 CUDA API 统计：每步有一次 `cudaStreamSynchronize`，约 1835 µs，而 SGLang 同样位置只有一次 event 等待，没有流同步。
  3. 读 FlashInfer 0.6 的 `decode.py` 源码：CUDA Graph 模式下拷贝 `kv_indices` 时，写的是 `non_blocking=(indices.device == self.device) and non_blocking`。也就是说，CPU 上的张量会走阻塞拷贝，阻塞拷贝就要等流上之前的所有工作完成。
- **后果**：主机每步都要等上一步 GPU 跑完才能继续，overlap 调度实际上没起作用。
- **做法**：调 `plan()` 之前，先把 `kv_indices` 异步拷到 GPU（`python/tandem/layers/flashinfer_attention.py` 的 `plan_decode`）。
- **效果**：
  - 0.6B 单路 2575 → 2323 µs，GPU 空闲 11.9% → 2.1%，反超 SGLang（2419 µs）。
  - 8B 单路 20,114 → 20,029 µs。
  - 0.6B 各格吞吐普遍提高 2–3 个百分点。
- **回归测试**：`test_steps_do_not_wait_for_queued_gpu_work`。先往 GPU 上排约 0.1 秒的空转，再跑一步 decode 和一步 prefill，返回时 GPU 必须仍在忙。为了确认测试本身有效，还做了对照：换回旧写法后，两种模型上测试都报错。
- **证据**：P1 对齐报告 §6.2；提交 `480e102`。
- **可能的追问**：
  - *为什么 non_blocking 从 pageable 内存拷贝不会同步，而阻塞拷贝会？* PyTorch 的阻塞拷贝是 `cudaMemcpyAsync` 加 `cudaStreamSynchronize`；非阻塞的 H2D 拷贝由驱动先拷进暂存缓冲区，不等流。
  - *怎么避免以后再出这种问题？* 靠上面那个回归测试，以及 `TANDEM_STEP_TIMING` 和 nsys 的 API 统计。

### 3.4 token 预算实验：为什么保持 2048 不改大

- **假设**：prefill 优先下，连续的 prefill 分块本来就是背靠背执行，预算大小不影响 decode 停多久，只决定同时到达的请求能并进几步。改成 8192 也许能减少开头一批请求的 TPOT 尾巴。
- **结果**：
  - 8B ShareGPT 并发 16 的 TPOT p99 从 1.07 降到 0.63，确实有效；
  - 但 8B 1024/256 并发 8 的 TTFT p50 从 0.84 涨到 1.26，超限。
- **原因**：输入长度固定的负载里，一批请求同时开始、同时结束，下一批也同时到达。预算大了，前面的请求要等整批 prefill 完才出首 token。
- **结论**：不改，保持 2048。面试时可以讲"一个看起来有效的改动，为什么最后没采用"。
- **证据**：P1 对齐报告 §6.3。

### 3.5 一个不达标的格子：判断它是噪声，不是性能问题

- **现象**：0.6B ShareGPT 并发 32 的 TPOT p99 是对手的 1.37 倍，是 P1 唯一没达标的格子。
- **定位**：写了引擎时间线追踪 `TANDEM_TRACE`，记录每个请求何时进入引擎、每一步包含哪些请求、首 token 何时发出。和客户端逐请求的数据用同一个时钟（perf_counter）对齐。
  - 每档开头 32 个请求同时到达，引擎分 4 步 prefill。
  - 先拿到首 token 的短回复请求，要等后面的 prefill 做完，空等 65–93 ms，TPOT 因此被拉高。
  - p99 就是第二差的那个请求，所以结果完全取决于排在前面的请求里有几个回复很短。
  - tandem 严格按客户端发送顺序处理；SGLang 进入调度器的顺序是打乱的，等于抽了不同的签。
- **证据**：换 7 组提示词，两家各跑两轮，共 14 组：中位数 tandem 14.01 ms、SGLang 13.70 ms，比值 1.02。SGLang 自己同一组提示词两轮之间最多差 40%。
- **结论**：这一格是统计波动，不是 tandem 慢。同一格其余指标 tandem 都更好：吞吐 1.07 倍，TTFT p50 0.85 倍。最后和项目负责人确认，按这个分析记录、判定 P1 达标。
- **证据位置**：P1 对齐报告 §4；`benchmarks/results/dumps-rep/`（本地，不进版本库）。
- **可能的追问**：*为什么不直接把这格调过？* 能调过的办法都会让别的指标变差（见 3.4）；为了让一个统计量好看而牺牲真实指标，不值得。

### 3.6 P2：小 batch 的 GEMV 内核

- **问题**：剖析 0.6B 单路 decode 每步约 2.3 ms：
  - 每层 4 个投影的 GEMM 共 49 µs，乘 28 层是 1368 µs，只读到约 644 GB/s；qkv、o、down 只有约 590–600 GB/s；
  - lm_head 已经到 877 GB/s。
  - batch 1–8 时投影是"读一遍权重"的带宽受限操作，cuBLAS 在这些小矩阵上不够好。
- **做法**（`python/tandem/layers/triton_gemv.py`）：
  - **CUDA 核心版**（batch 1–2 为主）：每个程序读 BLOCK_N 行权重，和 M 行输入在 float32 里做乘加，每个权重字节只读一次。有两种归约方式：每块 K 归约一次，或整段累加完再归约一次。
  - **tensor core 版**（batch 4–8 为主）：输入补到 16 行，用 `tl.dot`。batch 8 时 CUDA 核心算不过来（0.6–0.96 倍），换 tensor core 后反而全面胜出。
  - **配置搜索**（`benchmarks/bench_gemv.py`）：每个形状（N, K）× batch 都搜一遍分块、warp 数、流水级数和变体。测时在 CUDA graph 里轮换多份权重（总量 ≥96 MB），让每次都从显存读，避免 6 MB 的 L2 缓存把带宽测虚。
  - **查表分派**：只在比 cuBLAS 快 3% 以上的形状上用自写内核，其余仍走 cuBLAS；在 CUDA graph 里同样生效；可以用 `--no-small-batch-gemv` 关掉做对比。
- **效果**：
  - 内核本身比 cuBLAS 快 1.03–1.52 倍。例如 0.6B o_proj 在 batch 2 时，cuBLAS 掉到 438 GB/s，Triton 是 657 GB/s。
  - A1（512 进 / 512 出，TPOT p50，ms）：

| 模型 | batch | P2 前 | P2 后 | 最强对手（SGLang + compile） |
|---|---|---|---|---|
| 0.6B | 1 | 2.22 | 2.01 | 2.14 |
| 0.6B | 4 | 2.65 | 2.39 | 2.51 |
| 0.6B | 8 | 3.16 | 2.90 | 3.01 |
| 1.7B | 1 | 5.02 | 4.61 | 4.76 |
| 1.7B | 4 | 5.68 | 5.04 | 5.24 |
| 1.7B | 8 | 6.31 | 5.66 | 5.74 |

- **证据**：提交 `6b88705`；`benchmarks/results/p2-gemv*.jsonl`、`p2-a.jsonl`（本地）。
- **测试**：内核和 `F.linear` 对比；强制所有投影走自写内核时，贪心输出和 cuBLAS 一致，只允许在近似平局（FP32 下两个候选分数几乎相等）时不同。
- **可能的追问**：
  - *为什么 batch 小时 tensor core 反而不好？* M=1 时一个 MMA tile 16 行只用了 1 行，算力浪费不要紧，但要额外搬运；batch 8 时 CUDA 核心上每个权重要做 8 次乘加，加上类型转换就跟不上带宽了。
  - *为什么要轮换权重？* o_proj 只有 4 MB，反复读同一份会命中 L2，测出的带宽会虚高。

### 3.7 失败的尝试：把 norm 和激活融合进 GEMV（面试时讲失败也很加分）

- **想法**：每层有 3 个小内核（加残差 + RMSNorm 两次、SiLU×up 一次），各约 1.5–1.7 µs。在 GEMV 读输入时顺手算出来，就能省掉它们。
- **做法**：写了 `gemv_prologue`。每个程序先遍历一遍输入行算出 RMS，再在主循环里边归一化边乘权重；残差由 0 号程序写回。
- **微基准**：batch 1 时每对省 0.4–0.9 µs；batch ≥2 时反而更慢，因为每个程序都要重算一遍 norm。
- **放进真实 decode 后**：每步少了 84 个内核，但融合后的 GEMV 也变慢了差不多同样多，净省约 16 µs；单路 TPOT 反而从 2.01 变成 2.04。
- **结论**：关掉，代码和测试保留。教训是微基准的收益不一定能在整步里兑现，必须端到端复测。
- **证据**：`triton_gemv.py` 里 `FUSED_CONFIGS` 上方的注释；`benchmarks/results/p2-fused.jsonl`、`p2-profile.jsonl`（本地）。

### 3.8 P2：小 batch 的 decode attention（Triton split-KV）

- **问题**：剖析显示 0.6B 单路每层 attention 约 11–12 µs，而且不随上下文长短变化（512 到 1024 基本一样），说明主要是固定开销，不是读数据（只读 2–4 MB）。
  - FlashInfer 的规划器在单路 1K 上下文时把 KV 切成约 92 段，每段约一页，再做 92 路合并。
  - 换它的其它调用方式（关掉切分、改用 tensor core 内核、指定切分长度）都没有更快（`benchmarks/bench_decode_attn.py`）。
- **做法**（`python/tandem/layers/triton_decode_attn.py`）：
  - 每个程序处理一个（请求、KV 头）对和一段连续的页，同组 GQA 的 G 个 query 头放在寄存器里，用 exp2 做在线 softmax，float32 累加。
  - **单内核合并**：每段写完部分结果后，对计数器做一次 gpu 级的 acq_rel 原子加；最后一个完成的程序负责合并，合并时用 `.cg` 读，绕过 L1 避免读到旧数据，再把计数器清零，留给下一次 CUDA graph 重放。这是 CUTLASS split-K 信号量的模式，省掉一次合并内核的启动。
  - **分段数**：作为启动常量，每个 CUDA graph 档位固定一个值；运行时按实际页数平均分给各段，所以同一个 graph 适用任意上下文长度。
- **效果**：
  - 微基准：单路 512 上下文 11.6 → 7.8 µs（1.48 倍），1K 约 1.15 倍，2K–8K 持平（最多慢 2.5%）；batch 2 只在短上下文时更快；batch 4 起和 FlashInfer 互有胜负。
  - 所以只在 batch 1–2、GQA 比为 2（0.6B、1.7B）时启用。
  - 端到端：A1 单路 0.6B 2.01 → 1.99 ms，1.7B 4.61 → 4.58 ms。比微基准预期的小，因为 A1 的上下文在生成中从 512 涨到 1024，长的那一段优势变小。
- **测试**：和 float32 参考实现对比，覆盖打乱的页序、在页中间结束的上下文、分段数多于页数等情况，并检查计数器每次调用后都恢复为 0；端到端比较开关前后的贪心输出。
- **状态**：已提交（`831ecba`）。
- **可能的追问**：
  - *为什么需要内存序？* 合并的程序要读到其它程序写的部分结果，必须保证那些写对它可见：先 barrier，再做带 release 语义的原子操作，读的一方要有 acquire 语义。
  - *为什么单路仍然要 8–10 µs？* 页表、K/V、部分结果写回、合并，是几层串行的显存延迟，带宽只用到 270–430 GB/s。要进一步缩小，得靠持久化内核，把 attention 的延迟和下一层权重的预取重叠起来。

### 3.9 A2：支持 AWQ 4 bit 量化模型（W4A16）

- **背景**：A2 场景是 Qwen3-8B 的 4 bit AWQ 量化版在小 batch 下的速度。vLLM 和 SGLang 都把权重转成 Marlin 格式来跑，单路最好 7.22 ms/token，是带宽下限的 1.17 倍；目标是快 1.05 倍。tandem 原来不能加载量化模型。
- **AWQ 检查点格式**（AutoAWQ 的 gemm 格式）：
  - `qweight [K, N/8]`：沿输出维每 8 个 4 bit 权重打包成一个 int32，半字节顺序是 AWQ 特有的 `[0, 2, 4, 6, 1, 3, 5, 7]`；
  - `qzeros [K/128, N/8]`：零点，打包方式相同；
  - `scales [K/128, N]`：每 128 个输入一组；
  - 反量化：`w = (q - z) × s`。
- **为什么要在加载时重排**：原格式里，同一个输出的权重沿 K 方向相隔一整行，每行只有几个字节连续。小 batch 的 GEMV 要么读大量零碎的跨步数据，读显存效率很低；要么把 K 切成几段再归约，又多出几次内核启动。所以加载时一次性重排成"每个输出行沿 K 连续打包"的自定义布局（细节见下面第二阶段）。Marlin 也是在加载时把 AWQ 转换成自己的格式。
- **做法**（`python/tandem/layers/awq.py`、`python/tandem/layers/linear.py`、`python/tandem/csrc/w4_gemv.cu`）：
  - `W4Linear`：用检查点的原始张量作为缓冲区，由加载器填充；qkv、gate_up 沿输出维（列）拼接。加载完、放到 GPU 上之后，`finalize` 把它们重排成 `packed [N, K/8]`、`scales/zeros [N, K/128]`。
  - **不分配 dense 权重**：量化层直接创建 4 bit 缓冲区。原来的 dense 路径会先按 FP32 初始化全部权重，8B 模型要 32 GB 内存。
  - **decode（batch ≤16）**：自写的 CUDA C++ 内核边读 4 bit 边反量化，加载模型时用 `load_inline` 编译（不放到 CUDA graph 捕获期间）。按（N, K, batch）查表选内核和配置。
  - **prefill（batch >16）**：先用 Triton 内核反量化成 FP16，再交给 cuBLAS。没有 nvcc 的机器 decode 也走这条路。
- **测试**（`tests/test_awq.py`）：
  - 布局测试：直接按文档里的公式检查每个半字节存的是哪个 k；
  - 重排加反量化与参考公式一致；
  - CUDA 核心内核 batch 1–4、tensor core 内核 batch 1–16，每一种编译进去的配置都和反量化后的矩阵乘对比；覆盖 N 不是 16 的倍数、K 只有一个量化组等边界；
  - 输入没有 16 字节对齐时自动回退到反量化 + cuBLAS；
  - 端到端：把 tiny Qwen3 量化成 AWQ 检查点，tandem 加载后的贪心输出与反量化的 dense 模型一致（允许近似平局）。
- **真实模型**：Qwen3-8B-AWQ 加载 11 秒，显存 8.2 GiB，回答正确（例如 "The capital of France is Paris."）。
- **和 vLLM 逐 token 对比**：同样 5 个提示词，各贪心生成 64 个 token，320 个 token 全部一致。这是"实现正确"最直接的证据（`benchmarks/results/logs/awq-compare.out`，服务器上）。
- **第一版性能很差**：没调配置时单路 34.4 ms/token，对手 7.22 ms，只有 0.21 倍。4096 提示词的 TTFT 和对手接近（1009 vs 943–977 ms），说明 prefill 路径没问题，慢在 decode 的 W4 GEMV。

**第一阶段：CUDA 核心上的 W4 GEMV**（qkv 形状 6144×4096，单路，有效读带宽；目标约 780 GB/s）：

| 版本 | 带宽 | 改了什么、为什么 |
|---|---|---|
| Triton，每次只处理一个量化组 | 约 408 GB/s | 每轮只读 128 字节，延迟主导 |
| Triton，用魔数代替整数转浮点，分块加大到 1024 | 545 GB/s | Ampere 上整数转浮点（I2F）的吞吐只有 FP32 乘加的 1/4。把 4 bit 值按位或进 2^23 的浮点位模式再减去常数，就得到精确浮点；零点并进这个常数，反量化只剩"减一次、乘一次" |
| Triton，跨线程归约推迟到最后 | 592 GB/s | 原来每块 K 都做一次 warp 内的 shuffle 归约 |
| **CUDA C++，LOP3 反量化** | **761 GB/s**（gate_up 860） | 见下 |

- **第一版 CUDA 内核**（`python/tandem/csrc/w4_gemv.cu`，提交 `6b76a60`）：
  - 每个 lane 用一次 16 字节加载拿 32 个权重，一个 warp 一次连续读 512 字节；
  - 用 4 条 `lop3.b32` 把 8 个 4 bit 值直接拼进 half2(1024, 1024) 的位模式，得到 1024+q，没有任何类型转换；
  - 零点和缩放用 HSUB2/HFMA2 处理；每 8 个乘积在 FP16 里求和，再累加到 FP32；最后用 warp shuffle 归约。
- **AWQ 半字节顺序的秘密**（面试加分点）：AWQ 把 8 个输出打包成 `[0, 2, 4, 6, 1, 3, 5, 7]` 这种奇怪顺序，就是为了配合这个 LOP3 技巧。掩码 `0x000f000f` 一次取出第 0、4 号半字节，正好放进一个 half2 的高低两半；在 AWQ 顺序下，这两个位置存的是相邻的两个权重。所以我重排时也沿用这个顺序（沿 K 方向）。
- **各 batch 的带宽**：batch 1 为 749–860 GB/s，batch 2 为 648–795，batch 4 为 539–767，batch 8 只有 324–465。batch 8 时每个权重要做 8 次乘加，CUDA 核心上的乘加成了瓶颈。
- **端到端 A2**（512 进 / 512 出，TPOT p50）：batch 1 为 6.76 ms，是对手的 1.068 倍，达标；batch 4 为 8.60 ms（0.895 倍），batch 8 为 13.80 ms（0.648 倍），差得远。

**第二阶段：tensor core 内核（batch 1–16）**

- **为什么**：batch 8 时每读一个 4 bit 权重，CUDA 核心要做一次反量化加 8 次乘加，算不过来。tensor core 的乘加吞吐高一个数量级，问题变成"怎么把 4 bit 权重高效地喂给 `mma.sync`"。
- **三个关键设计**（`python/tandem/csrc/w4_gemv.cu` 里的 `w4_mma_kernel`）：
  1. **权重从显存直接读进 MMA 片段，不经过 shared memory**：`mma.m16n8k16` 的 A 片段里，lane (g, c)（g = lane/4，c = lane%4）持有第 g、g+8 行的 k = 2c、2c+1、2c+8、2c+9。重排时让每个 lane 需要的权重正好落在它自己的 16 字节里，一次加载、LOP3 反量化后直接当 A 片段。decode 时每个权重只用一次，没有复用，进 shared memory、再 ldmatrix 只会多搬一次。
  2. **k 置换**：MMA 对 16 个 k 求和，和顺序无关，只要 A 和 B 用同一个置换。所以规定 lane c 的 4 个逻辑 k 对应物理上连续的 `8c + 4s + {0..3}`（s 是第几个 k16 步）：
     - 权重：每个 int32 存 8 个连续的 k，半字节顺序正好是 LOP3 要的 `[0, 2, 4, 6, 1, 3, 5, 7]`（和 AWQ 原来沿 N 方向的顺序一样，只是改成沿 K）；
     - 输入 x：每个 lane 每 32 个 k 只要一次 16 字节加载，同一行的 4 个 lane 正好读一段连续的 64 字节；
     - 正确的条件：同一个逻辑 k 在所有 lane 上必须对应同一个物理 k。这个置换只依赖 c 和 s，不依赖行号 g，所以成立。
  3. **swap AB：权重当 A，batch 当 N**：常规做法是 x 当 A（16 行）、权重当 B（8 列），batch ≤8 时 x 要补零到 16 行，一半 MMA 白算。反过来让 16 个输出行当 A，batch 落在 n = 8 那一边，batch 8 正好填满，MMA 数量减半。3090 是 GeForce 卡，FP32 累加的 tensor core 吞吐只有 FP16 累加的一半（71 vs 142 TFLOPS）。按补零方案，qkv 一次要算 0.8 GFLOP，约 11 µs，接近读权重的 15 µs；减半后才有足够余量，而且不用为了速度改成 FP16 累加、牺牲精度。
- **并行方式**：一个 CTA 算 16 个（或 32 个）输出行；CTA 里的 WARPS_K 个 warp 沿 K 按量化组切分，每个 lane 同时有 UNROLL 个组在途，最后在 shared memory 里把各 warp 的部分和加起来。batch 9–16 用两个 n = 8 的 tile。
- **第一版 tensor core 内核的结果**：batch 8 时每层 4 个投影合计 135.9 µs，比 CUDA 核心版快得多，端到端 batch 4、8 从 0.90、0.65 倍提到 1.025、1.000 倍，但还没到 1.05。batch 1 反而比第一阶段的 GEMV 慢 2%（6.88 vs 6.76 ms）。
- **再优化：权重绕过 L1**（`ld.global.nc.L1::no_allocate`）：
  - batch 8 时，每读 256 字节权重，要从 L1 读 512 字节 x（8 行 × 64 字节）。x 每个 CTA 都要读一遍，靠 L1 命中才便宜；
  - 但权重用 `__ldg` 读也会进 L1，一次性的流式数据把 x 挤了出去；
  - 改成权重不在 L1 分配之后，batch 8 每层从 135.9 µs 降到 127.4 µs（−6%），batch 16 从 183.8 降到 164.2；
  - 同样的改动让 CUDA 核心版在 batch 1 又略快于 tensor core 版（每层 123.1 vs 125.3 µs），所以 batch 1 查表走 CUDA 核心；
  - 另外试了"每个 warp 算两个 16 行 tile、x 片段复用两次"，只在 batch 16 的 gate_up 上更快。
- **最终微基准**（Qwen3-8B 的 4 个投影，µs；`benchmarks/bench_w4.py`，轮换多份权重避免 L2 命中；每格取两种内核里更快的）：

| 投影（N×K） | batch 1 | batch 4 | batch 8 | batch 16 | cuBLAS FP16，batch 8 |
|---|---|---|---|---|---|
| qkv 6144×4096 | 16.9（792 GB/s） | 17.4 | 17.3 | 21.1 | 60.6 |
| o 4096×4096 | 11.8（753） | 12.0 | 12.1 | 15.9 | 45.0 |
| gate_up 24576×4096 | 61.8（865） | 63.5 | 63.9 | 81.5 | 244.9 |
| down 4096×12288 | 32.5（822） | 33.7 | 34.1 | 45.9 | 139.4 |

  - batch 1 到 8，每层 4 个投影合计只从 123.1 µs 涨到 127.4 µs（+3.5%），基本就是"读一遍权重"的时间；
  - batch 8 时比 cuBLAS 跑 FP16 权重快 3.5–4.1 倍（权重只有 1/4 大小）；
  - 同一布局下的 CUDA 核心版，batch 4 时 qkv 要 21.1 µs（tensor core 17.4），batch 越大差得越多。

- **正确性复核**：换成最终内核后，和 vLLM 在同样 5 个提示词上逐 token 对比，仍然 320/320 一致（`benchmarks/results/logs/awq-compare-w4d.out`，服务器上）。
- **剩下的差距在哪**（nsys 逐算子剖析，`benchmarks/profile_engine.py`，每个 decode 步，µs；`benchmarks/results/p2-profile-awq.jsonl`）：

  - SGLang 在 nsys 下跑 batch 8 时服务崩溃，没拿到它 batch 8 的分解。
- **一个容易误判的点：c8 的 TPOT 不等于 decode 一步的时间**：
  - c8 时 tandem 的 TPOT p50 是 8.75 ms，但 ITL p50（相邻两个 token 的间隔，基本就是一个 decode 步）只有 8.08 ms；SGLang 也一样（8.94 vs 8.33）；
  - 差的 0.6–0.7 ms 来自别的请求的 prefill 步插在中间：一批 8 个 512 token 的请求要分两步 prefill（token 预算 2048），先 prefill 的那 4 个请求，要等第二步 prefill 完才能继续 decode，这段停顿被摊进它们的 TPOT；
  - 所以只看 decode 步，tandem 在 c8 已经快 3%（8.08 vs 8.33）；要让 TPOT p50 到 1.05 倍，decode 步还要再省约 0.24 ms。
**第三阶段：把 decode 步里的小内核去掉或换快的**（目标：c4、c8 再省 0.08、0.24 ms）

1. **SwiGLU 融合进 gate_up 内核的收尾**（`w4_mma_kernel` 的 `act`，`awq.py` 的 `interleave_gate_up`）：
   - 做法：加载时把 gate、up 的权重行交错成每 16 行一组（前 8 行 gate、后 8 行对应的 up）。MMA 的 D 片段里，同一个 lane 的 d0 和 d2 正好是同一个特征的 gate 和 up，于是直接在 FP32 累加器上算 silu(gate)·up，只写 [M, 12288] 的结果；
   - 为什么：激活内核每层 3.3–3.5 µs，几乎都是启动和延迟；融合后 gate_up 的 [M, 24576] 中间结果也不用写回显存；数值上少一次 FP16 舍入，反而更准；
   - prefill 路径：反量化时把行写回原来的 [gate | up] 顺序，再用 FlashInfer 的 silu_and_mul，和融合前完全一样（第一版用跨步视图做 silu·up，多了两次读写，4096 提示词的 TTFT 慢了 1.8%，复测发现后改掉了）；
   - 微基准（gate_up，µs，`p2-w4e.jsonl`）：融合版和不融合的单独内核一样快，收尾等于白送；每层省掉激活内核的 2.3（batch 1）到 3.3 µs（batch 8）。
2. **attention：batch ≥ 8 时 KV 不切分**（`FlashInferAttentionBackend.nosplit_min_batch`，`cuda_graph.py`）：
   - 发现：FlashInfer 在 CUDA graph 模式下的默认规划总是 split-KV + merge。batch 8 时每个请求只切 2 段，多出的部分结果读写和 merge 内核比切分带来的并行收益还大；
   - 微基准（8B 的头，`p2-attn-8b-nosplit.jsonl`，切分耗时 / 不切分耗时）：batch 8 在 512、1024 上下文是 1.086、1.053，2048 持平，4096 是 0.956；batch 4 不切分慢 25%–47%（CTA 太少）；
   - 难点：CUDA graph 把捕获时的内核序列固定死了（有没有 merge），不能每步改规划方式；FlashInfer 文档也写了 fixed_split_size 不保证兼容 graph，而 `disable_split_kv` 是 graph 安全的；
   - 做法：batch ≥ 8 的档位各多捕获一个"不切分"的 graph，配自己的 decode wrapper；每步按最长上下文选，≤ 2048 用不切分，否则用默认的。两个 wrapper 各有规划缓冲区，overlap 调度下交替使用也不会互相覆盖；
   - 测试：把阈值调到 32，让上下文在生成中途越过阈值，用计数器确认两种 graph 都被重放过，输出和只用默认规划的引擎一致；
   - 实际效果比微基准小：剖析显示 batch 8 的 merge 内核没了，但不切分时 attention 内核本身每层慢了 1.8 µs，净省约 1.5 µs/层。原因还没细查：微基准里每个请求的 KV 页是连续的、长度相同，真实请求的页是分散的、长度也不一样。
3. **残差加 RMSNorm 换成 Triton**（`triton_ops.fused_add_rmsnorm`，`--no-small-batch-norm` 可关）：
   - 发现：FlashInfer 的 `fused_add_rmsnorm` 在 batch 1 是 2.37 µs，batch 8 变成 3.07 µs，行没有并行展开；8B 每步要调 72 次；
   - 做法：每行一个 Triton 程序，语义和 FlashInfer 完全一致（FP32 求和，residual 原地写回，输出用未舍入的和），batch ≤ 64 用它，prefill 仍走 FlashInfer；
   - 微基准（`benchmarks/bench_norm.py`，`p2-norm.jsonl`）：所有 decode batch 都快 1.2–1.7 倍（hidden 4096、batch 8：2.86 → 1.92 µs），residual 逐位相同，输出最多差 1 个 ulp；0.6B、1.7B 也受益。
4. **每步一次的小开销**：
   - 全贪心的步直接在 FP16 logits 上做 argmax，省掉一次 FP32 拷贝（batch 8 约 10 µs；转换是精确的，选出的 token 不变）；
   - embedding：`nn.Embedding` 底层的 index_select 内核随行数线性变慢（CUDA graph 里 1/8/16 行是 1.8/5.3/9.4 µs），高级索引 `weight[ids]` 从 2 行起都是 1.4 µs，但 1 行时反而要 2.8 µs，所以按行数二选一（实测见 `benchmarks/results/logs/p2-embed.out`，服务器上）；
   - lm_head（151936×4096）：Triton GEMV 在两种 dtype、batch 1/2/4/8 共 8 格里都比 cuBLAS 快 1.8%–2.7%。配置表原则上要快 3% 才收录，这里作为例外收进去：8 格方向一致，而且 1.4 ms 的内核快 2% 就是 26–38 µs（`p2-gemv-lmhead.jsonl`）。
5. **对其它模型的影响（回归检查）**：
   - Triton norm 对所有模型生效：A1 里 0.6B 三格持平（1.99/2.38/2.90 ms），1.7B 的 c4、c8 从 5.04、5.66 降到 5.00、5.61；
   - 不切分的 graph 对 8B BF16 也生效：同一会话里开、关各跑一遍（1024/256 和 256/1024，并发 8、16），4 格都快 0.2%（每步约 0.05 ms），没有变差的格子（`p2-8b-nosplit.jsonl`）。

- **阶段结果**（A2，TPOT p50，ms；每格 3 次取中位数）：

| batch | 对手 | 第二阶段结束 | +SwiGLU 融合、不切分 | +Triton norm | +argmax、embedding、lm_head | 相对对手 | 目标 ≥1.05 |
|---|---|---|---|---|---|---|---|
| 1 | 7.22 | 6.74 | 6.65 | 6.62 | **6.61** | **1.092 倍** | 达到 |
| 4 | 7.70 | 7.41 | 7.30 | 7.23 | **7.20** | **1.069 倍** | 达到 |
| 8 | 8.94 | 8.75 | 8.64 | 8.57 | **8.53** | **1.048 倍** | 差 0.02 ms |

- **正确性复核**：最终配置下（SwiGLU 改在 FP32 累加器上算，数值有细微变化）和 vLLM 再逐 token 对比一次，仍然 320/320 一致（`benchmarks/results/logs/awq-compare-w4h.out`）；GPU 上全部 92 项测试通过。
- **还没解决的**：
  - c8 还差 0.02 ms（0.2%）。decode 步本身已经比 SGLang 快 6%（ITL p50 7.86 vs 8.33），差距在 TPOT 里那段 prefill 停顿（tandem 0.67 ms，SGLang 0.61 ms）：AWQ 的每个 prefill 分块都要先反量化全部权重，tandem 的 prefill 步比 SGLang 的长约 6%；
  - 4096 提示词的 TTFT 是对手的 0.79–0.94 倍，原因相同：每个 prefill 分块多花约 26 ms 做反量化（4096 token 的 prefill 里约占 5%，512 token 的 prefill 里约占 18%）。要用 Marlin 那样的融合反量化 GEMM 才能根治。放到另一个 stream 上和前一层 GEMM 重叠的办法估计行不通：cuBLAS 的大 GEMM 把每个 SM 的寄存器和 shared memory 都占满了，反量化的 CTA 挤不进去；
  - 步与步之间 GPU 还空着约 24 µs（nsys 的逐内核时间线）：graph 启动延迟 8.3 µs，argmax、拷回 token、下一步输入拷贝之间各 5–6 µs，是拷贝引擎和计算引擎交接的延迟。把每步的几次小拷贝合并成一次能省一部分。
- **可能的追问**：
  - *为什么不用 shared memory 和 ldmatrix？* Marlin 面向更大的 batch，多个 M tile 复用同一份权重，还要多级流水，所以要用 shared memory。decode 时每个权重只乘一次，直接读进寄存器最省。
  - *k 置换为什么不改变结果？* 矩阵乘是 Σ_k A[m][k]·B[k][n]，对 k 换顺序不影响和；只要 A、B 的每个逻辑 k 都指向同一个物理 k 就行。
  - *batch 1 时 tensor core 浪费了 7/8，速度如何？* 和 CUDA 核心版只差 2%：两者都受带宽限制，tensor core 的算力浪费不要紧。batch 1 查表选更快的 CUDA 核心版，batch 2 起都是 tensor core 更快。
  - *为什么权重绕过 L1 能快 6%？* L1 只有 128 KB，权重是只读一次的流式数据，缓存它没有任何好处，还会把每个 CTA 都要反复读的 x 挤出去。这和 CPU 上的 non-temporal load 是一个道理。

## 4. 基线测量里的发现（P0，说明"我知道对手强在哪"）

- **0.6B 上 SGLang 每格比 vLLM 快 6%–22%**。剖析显示两家的 GEMM 内核完全一样，差距主要在 decode attention：vLLM 用 FlashAttention-2 的 split-KV，SGLang 用 FlashInfer；0.6B 单路分别是 551 µs 和 339 µs。8B 上每步 20 ms，这点差距被摊薄，两家打平（P0 基线报告 §5）。
- **8B BF16 单路已经接近带宽下限**：每 token 读 15.1 GB 权重，20.1 ms，约 750 GB/s，是实测拷贝带宽的 95%。所以 8B BF16 只要求对齐，超越的空间在小模型和量化模型上。
- **A 场景**：最强对手是 SGLang + torch.compile：0.6B 单路 2.14 ms，是带宽下限的 1.43 倍；1.7B 4.76 ms，只有 1.08 倍；8B AWQ 7.22 ms，1.17 倍。所以把目标修订为 0.6B 快 1.2 倍、1.7B 和 8B AWQ 快 1.05 倍（设计方案 §5.2）。
- **B 场景**：
  - 多轮对话的工作集超出显存后，只用显存的缓存命中率掉到 9%–10%，SLO 达标只有 66%–72%；
  - 两家加 30 GB 主机内存层后，命中率回到理想值的 90% 以上，SLO 达标 96%；
  - 所以 B 场景的空间在载入速度和尾延迟，不在命中率（P0 基线报告 §7）。

## 5. 工程上的坑（体现动手能力）

- **服务器不能上网，驱动 550 只支持到 CUDA 12.4，glibc 2.31**：
  - vLLM / SGLang 最新版都装不上，改用能装的最新版（vLLM 0.32 cu129、SGLang 0.5.10）；
  - 依赖按发布日期锁定，离线安装；修了三处"误装 CUDA 13 依赖"的问题（P0 基线报告 §3.5）。
- **模型传输**：经 VPN 上传只有约 1 MB/s。把 BF16 权重的高低字节拆开、只压缩高字节，体积降到原来的 72%；支持断点续传，服务器端逐个核对 SHA-256。
- **nsys 在 vLLM 里采集不到**：见 2.3。
- **剖析数据要按"整步"切分**：窗口两端会截到半步，按每次 graph launch 的完整内核数折算。
- **测试里的近似平局**：两个 BF16 后端在 FP32 下前两名分数只差 0.001 时，选哪个都对。所以贪心对比测试以 FP32 参考模型为准：允许第一处分歧发生在近似平局上，这也是 vLLM 测试的做法（`assert_same_or_near_tie`）。

## 6. 高频问题速答

| 问题 | 回答要点 |
|---|---|
| 和 vLLM / SGLang 比，你的优势是什么？ | 只针对一个模型家族，可以按形状专门调内核；小 batch 的 GEMV 和 attention 都是查表选最优配置。数据见 3.6、3.8 |
| 连续批处理和静态批处理的区别？ | 每一步重新组 batch，完成的请求随时退出、新请求随时加入，GPU 不用等最慢的请求 |
| 分页 KV 解决什么问题？ | 显存碎片：KV 按页分配，请求长度不用事先预留；前缀缓存可以按页共享 |
| prefill 和 decode 的瓶颈有什么不同？ | prefill 受算力限制（大 GEMM）；decode 受带宽限制（每步把权重和 KV 读一遍） |
| CUDA Graph 为什么能加速？ | 把一步里几百次内核启动录成一次重放，省掉 CPU 的启动开销；对 0.6B 这种小模型至关重要 |
| overlap 调度是什么？ | CPU 准备第 N+1 步时，GPU 正在算第 N 步；上一步的 token 留在 GPU 上直接当下一步的输入 |
| 为什么分 API 进程和引擎进程？ | GIL 争用，见 1.1 |
| 你遇到最难的 bug？ | 3.3 的隐藏同步 |
| 如何验证正确性？ | float64 下 logits 与 HF 一致；GPU 上贪心输出与 FP32 参考一致（允许近似平局）；overlap 与同步执行逐 token 一致；关键内核各有单测；GPU 上共 92 项测试 |
| 怎么做性能分析？ | nsys 看内核时间和 GPU 空闲；`TANDEM_STEP_TIMING` 看 CPU 各环节；`TANDEM_TRACE` 看每步组成 |
| 一次优化没效果怎么办？ | 3.7：微基准有效、端到端无效，就回退，并记录原因 |
| tensor core 怎么用在小 batch 的 GEMV 上？ | 3.9 第二阶段：权重按 MMA 片段布局重排后直接读进寄存器；用 k 置换让 x 也能 16 字节加载；swap AB，权重当 A、batch 当 N，batch ≤8 不补零 |
| 量化模型怎么证明算对了？ | 和 vLLM 同样提示词逐 token 对比 320/320 一致；单测覆盖布局公式、每种内核配置、边界形状 |
| 还能怎么优化？ | 持久化内核（一个常驻内核跑完整步，消除内核间空隙，重叠 attention 延迟和权重预取）；AWQ prefill 用融合反量化的 GEMM（TTFT 和 c8 的 prefill 停顿）；合并每步的小拷贝（步间约 24 µs 空档）；多级 KV 存储（P3） |
| 一个 1.4 ms 的内核只快 2%，为什么也要？ | 绝对值是每步 30 µs，比很多整个内核都大；8 个格子方向一致才收录，并在配置表里写明为什么破例 |
