# P3 实施计划：多级 KV 存储（2026-11-13）

> 对应设计方案 §4.4（KV 缓存与多级存储）、§4.2 的 P3 改造、§5.2 的 B1 / B2 目标。B 场景的负载和对手基线见 P0 基线报告 §7。

## 1. 目标（设计方案 §5.2）

| 场景 | 条件 | 目标 | 对手（主机层 30 GB） |
|---|---|---|---|
| B1 多轮对话 | Qwen3-8B BF16，显存 KV 32,992 token，192 个会话（工作集约为显存 KV 的 4.5 倍），主机内存 30 GB | TTFT p50 比同预算的分层缓存快 ≥1.2 倍（对 SGLang HiCache 即 ≤130 ms），SLO 达标 ≥98% | SGLang 156 ms / SLO 96%；vLLM 302 ms / 96% |
| B2 共享长文档 | 32 篇平均 1.7 万 token 的文档，Zipf 访问，0.1 req/s | TTFT p50 ≤1.96 s | SGLang 2.82 s；vLLM 3.56 s |
| 无复用负载 | 1024/256，并发 16 | 加主机层后吞吐下降 ≤2% | 对手下降 1.1%–1.9% |

SLO：TTFT ≤2 s 且 TPOT ≤100 ms。L3（NVMe）这台机器做不了（系统盘是机械硬盘，比重算还慢），先不做。

## 2. 步骤

1. **起点**（进行中）：OpenAI 接口返回 `prompt_tokens_details.cached_tokens`；`run_reuse.py` 支持 tandem；跑 tandem 只用显存的 B1 / B2，确认起点和对手的只用显存配置相当。
2. **L2 主机层（MVP）**：主机 KV 池、radix 树分级、显存淘汰时不丢而是留在 L2、命中 L2 时异步载回。
3. **调度协同**：载入中的请求不挡其他请求；限制同时载入的数量；按层流水载入；缓存压力大时按最长前缀优先。
4. **B1 / B2 复测和调优**：会话感知的保留和预取、按访问频率保留文档；量化无复用负载的代价。

## 3. L2 的关键设计

- **主机 KV 池**（`tandem/cache/host_pool.py`）：一块 pinned 内存，page-first 布局 `[页, 层, K/V, 16 token, KV 头, 维度]`，一页包含所有层，整页读写；8B 每页 2.36 MB，30 GB 约 1.27 万页、20 万 token。用现有的 `BlockAllocator` 管理主机页号。
- **拷贝内核**（`tandem/csrc/kv_io.cu`）：显存里是每层一个张量（layer-first，FlashInfer 要求），两种布局之间用 GPU 内核直接读写 pinned 内存（UVA 下主机指针在 GPU 上可直接访问），一次启动搬完一批页的所有层，不用发几千次 `cudaMemcpy`。这是 HiCache 的做法。在专用的 CUDA stream 上执行，用 event 跟踪完成。
- **radix 树分级**（`tandem/cache/radix_cache.py`）：每个节点除了显存块号，再记主机页号；节点可以只在 L1、同时在 L1 和 L2、或只在 L2。约束：L1 里的节点构成从根开始的前缀闭集合（父节点在 L1 子节点才能在 L1），按 LRU 从 L1 子树的叶子淘汰。
- **写入策略**：
  - write-through：请求结束时把它的整页 KV 异步写到 L2（多轮对话的下一轮、文档问答的下一次都会复用），这样显存淘汰时只需丢掉 L1 那份，不用临时拷；
  - 淘汰时还没写到 L2 的节点（比如还没轮到写），先写再丢；L2 满了按 LRU 淘汰只在 L2 的节点。
- **载入**：
  - 请求命中的路径上有只在 L2 的节点时，先分配显存块、在拷贝 stream 上发起载入，请求进入"载入中"，不占这一步的预算；每步检查 event，载完再进入可调度集合；
  - 载入期间锁住路径，L2 的页不会被淘汰，L1 的新块也不会被别人用；
  - 写回中的显存块要等 D2H 完成才能还给空闲列表。
- **代价估计**（设计方案 §4.4）：PCIe 3.0 实测 12.9 GB/s，8B 每 1K token 的 KV 151 MB，载入约 12 ms；重算 1K token 约 0.29 s，载入快约 25 倍，所以 L2 命中一律载入。
- **测试**：radix 分级逻辑在 CPU 上单测（淘汰、写回、载入、加锁）；拷贝内核和逐页结果对比；端到端：命中 L2 后的贪心输出和不带缓存时逐 token 一致。
