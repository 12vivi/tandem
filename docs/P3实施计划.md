# P3 实施计划：多级 KV 存储（2026-11-13，2026-11-16 完成）

> 对应设计方案 §4.4（KV 缓存与多级存储）、§4.2 的 P3 改造、§5.2 的 B1 / B2 目标。B 场景的负载和对手基线见 P0 基线报告 §7。

## 1. 目标（设计方案 §5.2）

| 场景 | 条件 | 目标 | 对手（主机层 30 GB） |
|---|---|---|---|
| B1 多轮对话 | Qwen3-8B BF16，显存 KV 32,992 token，192 个会话（工作集约为显存 KV 的 4.5 倍），主机内存 30 GB | TTFT p50 比同预算的分层缓存快 ≥1.2 倍（对 SGLang HiCache 即 ≤130 ms），SLO 达标 ≥98% | SGLang 156 ms / SLO 96%；vLLM 302 ms / 96% |
| B2 共享长文档 | 32 篇平均 1.7 万 token 的文档，Zipf 访问，0.1 req/s | TTFT p50 ≤1.96 s | SGLang 2.82 s；vLLM 3.56 s |
| 无复用负载 | 1024/256，并发 16 | 加主机层后吞吐下降 ≤2% | 对手下降 1.1%–1.9% |

SLO：TTFT ≤2 s 且 TPOT ≤100 ms。L3（NVMe）这台机器做不了（系统盘是机械硬盘，比重算还慢），先不做。

## 2. 步骤和进展

1. **起点**（完成）：OpenAI 接口返回 `prompt_tokens_details.cached_tokens`；`run_reuse.py` 支持 tandem。tandem 只用显存时和对手持平：B1 32/96/192 会话 TTFT p50 102/162/464 ms（SGLang 110/166/440），B2 0.1 req/s 5.90 s（5.89）。
2. **L2 主机层第一版**（完成，提交 `6dd4427`）：主机 KV 池、radix 树分级、write-through、"载入中"列表。B1 192 会话 203 ms / SLO 95.6%，B2 3.26 s，都还不如 SGLang；无复用吞吐 −1.8%，但 TTFT p50 涨了 18%。
3. **第二轮到最终版**（完成）：生成的 token 不再 write-through；同一步按层载入；写回走拷贝引擎、载入只开 4 个 CTA、两条 stream；修复淘汰卡住的缺陷；短 prefill 优先、单独成步、为其抢占长 prefill；入队前检查；推迟调度（decode 步和长 prefill 步）。每一轮的问题见 §4 和 `docs/P3分层缓存报告.md` §5。
4. **结果**（`docs/P3分层缓存报告.md`）：B2 0.1 req/s TTFT p50 0.96 s（目标 ≤1.96 s，达到）；B1 192 会话 SLO 99.1%（目标 ≥98%，达到），TTFT p50 133 ms（目标 ≤130 ms，差 3 ms）；无复用吞吐 −0.2%（目标 ≤2%，达到）。判定：部分达成。
5. **没做的**：按访问频率保留（离线模拟：B2 能从理想命中的 73% 提到 74%–76%，但对 B1 有副作用）、会话感知的预取、L3。

## 3. 关键设计（当前版本）

- **主机 KV 池**（`tandem/cache/host_pool.py`）：用 `cudaHostAlloc` 按精确大小分配的 pinned 内存（PyTorch 的 pinned 分配器会向上取整到 2 的幂，30 GB 会占 34 GB），page-first 布局 `[页, 层, K/V, 16 token, KV 头, 维度]`，一页包含所有层，整页读写；8B 每页 2.36 MB，30 GB 约 1.27 万页、20 万 token。用现有的 `BlockAllocator` 管理主机页号。释放推迟到下一次分配（CUDA graph 捕获期间不能调用 `cudaFreeHost`）。
- **拷贝**（`tandem/csrc/kv_io.cu`）：显存里是每层一个张量（layer-first，FlashInfer 要求）。都在专用的 CUDA stream 上执行，先等计算 stream 上已入队的所有步。
  - 载入（主机 → 显存）：GPU 内核直接读 mapped 的 pinned 内存，每层一次启动、每层记一个 event；只开 4 个 CTA（2 个就能跑满 PCIe 12.3 GB/s；同时跑的矩阵乘法慢 2.4%，开 32 个慢 19%）。
  - 写回（显存 → 主机）：内核先把页在显存里聚成 page-first 的一块（38 MB 暂存区），再用拷贝引擎 `cudaMemcpyAsync` 写出去，12.6 GB/s。SM 直接往主机内存写，同时跑的矩阵乘法会慢 1–4 倍。
- **radix 树分级**（`tandem/cache/radix_cache.py`）：每个节点除了显存块号，再记主机页号；节点可以只在 L1、同时在 L1 和 L2、或只在 L2。约束：L1 里的节点构成从根开始的前缀闭集合，按 LRU 从 L1 子树的叶子淘汰。
- **写入策略**：
  - write-through：prompt 算完时异步写到 L2，显存淘汰时只需丢掉 L1 那份；
  - 生成的 token 不写（下一轮的 prompt 很少逐 token 包含它们，写了会把有用的 prompt 挤出主机层），只在被显存淘汰、而主机层还有空闲页时写回；
  - 抢占时把整个请求写出去（换出）；
  - L2 满了按 LRU 淘汰；L1 淘汰时的写回只用空闲主机页，不挤 L2 里的东西。
- **载入**（`tandem/scheduler/scheduler.py`、`executor/model_runner.py`）：
  - 请求命中的路径上有只在 L2 的节点时，分配显存块、发起按层载入，请求直接在这一步入队；
  - 这一步的前向在第 i 层开始前等第 i 层的 event（`ForwardContext.layer_waits`）；走 CUDA graph 的步在重放前等全部载完；
  - 载入必须排在正在跑的那一步后面：overlap 调度下，刚释放的块还可能被正在跑的那一步写一次。
- **短 prefill 优先**：等待队列前 8 个请求里，复用缓存后只剩 ≤512 token 要算、而且显存放得下的，排在正在分块 prefill 的长请求和它前面的等待请求之前。
- **代价估计**（设计方案 §4.4）：PCIe 3.0 实测 12.9 GB/s，8B 每 1K token 的 KV 151 MB，载入约 12 ms；重算 1K token 约 0.29 s，载入快约 25 倍，所以 L2 命中一律载入。

## 4. 第一轮暴露的问题

| 现象 | 原因 | 改法 |
|---|---|---|
| B1 192 会话命中只有理想的 88% | 请求结束时把生成的 token 也写进主机层：192 个会话共生成 26.2 万 token，超过主机层容量（20.3 万），按 LRU 挤掉了有用的前缀 | 生成的 token 不再 write-through |
| 命中主机层的 TTFT 比命中显存的多约 100 ms | 载入完要等下一次调度才放回队列，再下一步才 prefill；载入本身还要排在正在跑的那一步后面 | 同一步入队，前向按层等待 |
| 无复用负载 TTFT p50 涨 18% | 拷贝内核每页每层一个 CTA（写回 1024 token 是 4608 个），等 PCIe 时占满了 SM；SM 往主机内存写还会堵住片上的写队列 | 写回改用暂存区加拷贝引擎；载入只开 4 个 CTA |
| B2 命中的请求 TTFT 也要几秒 | 没命中的文档 prefill 要分 8–9 步，每步拿走全部 2048 预算 | 短 prefill 优先 |

## 5. 测试

- radix 分级逻辑在 CPU 上用假主机层单测（写回、淘汰到 L2、载回、主机层满、L2 的 LRU、接管只在 L2 的节点、拆分节点）；短 prefill 优先的调度测试。
- 端到端（CPU 引擎）：前缀被挤出显存后从主机载回，输出和不带缓存时逐 token 一致；抢占后从主机副本恢复，输出不变。
- GPU：拷贝内核的 page-first 布局和往返结果；按层等待（拷贝 stream 先空转约 10 ms 再载入，没等到的层会读到旧数据），eager 和 CUDA graph 两条路径；捕获期间释放主机池。
- 基准：`benchmarks/bench_kv_io.py`（带宽、对计算的干扰）；`benchmarks/run_reuse.py`（B1 / B2 / 无复用，结果在 `benchmarks/results/p3-b*.jsonl`，逐请求记录在 `p3-b-requests.jsonl`）。
