# P3 分层 KV 缓存报告（2026-11-16）

> 对应设计方案 §4.4（KV 缓存与多级存储）、§4.2 的 P3 改造、§5.2 的 B1 / B2 目标。实施计划和设计细节见 `docs/P3实施计划.md`。
>
> 对手数据沿用 P0 基线报告 §7（vLLM 0.32.0、SGLang 0.5.10，过渡版本），条件完全相同。

## 1. 结论

- **B2 共享长文档（0.1 req/s）**：TTFT p50 **0.96 s**，目标 ≤1.96 s，**达到**。
  - 比 SGLang 的分层缓存（HiCache，2.82 s）快 2.94 倍，比只用显存的 SGLang（5.89 s）快 6.1 倍；vLLM 分层缓存 3.56 s；
  - 命中是理想的 73%，和 SGLang 一样（vLLM 71%）；差别在命中的请求很快：45 个命中请求的 TTFT 中位数 279 ms，不再被没命中的长文档挡住；
  - SLO 达标 53.8%（SGLang 43.8%）。没命中的请求要重算 1.7 万 token 的文档，TTFT 都在 2.6 s 以上，这一项受限于主机层容量（只放得下约 12 篇文档）。
- **B1 多轮对话（192 会话）**：TTFT p50 **133 ms**，比 SGLang 分层缓存（156 ms）快 1.17 倍，目标 1.2 倍（≤130 ms）**未达到**，差 3 ms；SLO 达标 **99.1%**，目标 ≥98%，**达到**（SGLang 96.3%、vLLM 96.0%）；TTFT p99 1973 ms，约为对手的一半（SGLang 4076、vLLM 3785）；命中是理想的 95%（SGLang 90%、vLLM 98%）。
- **无复用负载**：加主机层后吞吐 −0.2%（目标 ≤2%，**达到**；对手 −1.1% / −1.9%），TTFT p50 +1.5%。
- **判定：P3 部分达成**。B2 和无复用代价达标；B1 的 SLO 达标、TTFT p50 差 3 ms。B1 中位数请求的 TTFT 大部分是它自己的 prefill 计算（新增 256–512 token 时约 100 ms），剩下能压的调度等待已经不多（§6）。
- **正确性**：GPU 上 116 项测试通过；主机层命中后的贪心输出和不带缓存时逐 token 一致（CPU 引擎，float64）或在近似平局内一致（GPU）；载入的按层等待用"拷贝 stream 先空转 10 ms"的测试验证。

## 2. 条件

- **模型与显存**：Qwen3-8B BF16，GPU 上的 KV 固定为 32,992 token（同 P0），打开前缀缓存；主机内存层 30 GB（约 20.3 万 token），三家相同。tandem 用 `--host-kv-gb 30`，vLLM 用原生 KV offloading，SGLang 用 HiCache。
- **B1 多轮对话**（`benchmarks/bench_reuse.py multiturn`）：ShareGPT 中至少 4 轮的对话，每轮发送完整历史（上一轮的提示词 + 数据集里的回复 + 本轮用户输入）；会话在 60 s 内均匀开始，思考时间服从均值 60 s 的指数分布；会话数 32、96、192，只统计第 2 轮起的请求。
- **B2 共享长文档**（`bench_reuse.py docs`）：32 篇随机 token 的文档（平均 16,855 token，共约 54 万），按 Zipf(1.0) 选文档，后接 48 token 的问题，输出 64 token；泊松到达，0.3 和 0.1 req/s；前 16 个请求作热身，统计后 80 个。
- **指标**：SLO 为 TTFT ≤2 s 且 TPOT ≤100 ms；命中率 = 引擎报告的缓存命中 token / 提示词 token，"理想"是缓存无限大时能命中的比例。场景压测时间长（每档 6–16 分钟），每档跑 1 次。
- **无复用负载的代价**：随机 1024/256、并发 16，重复 3 次，和 tandem 只用显存时比。
- **tandem**：本报告的最终版本（标签 `tandem-0.2.0.dev0-host30g-final`）。"只用显存"一行是 P3 开始时的版本（`-gpu`），作为起点。

## 4. 做了什么

### 4.1 主机内存层（L2）

- **主机 KV 池**（`tandem/cache/host_pool.py`）：`cudaHostAlloc` 按精确大小分配的 mapped pinned 内存（PyTorch 的 pinned 分配器会向上取整到 2 的幂，30 GB 会占 34 GB）。page-first 布局：一页 = 一个 GPU 块（16 token）在所有层的 K、V，8B 每页 2.36 MB，整页读写。释放推迟到下一次分配，因为 CUDA graph 捕获期间不能调用 `cudaFreeHost`。
- **radix 树分级**（`tandem/cache/radix_cache.py`）：每个节点记录显存块号和主机页号，可以只在 L1、两层都在、或只在 L2；L1 里的节点保持前缀闭合。L1 淘汰时有主机副本就只丢显存那份，没有就写回空闲主机页，都不行才删除；L2 满了按 LRU 淘汰。
- **写入策略**：prompt 算完时异步写到主机（write-through）；抢占时把整个请求写出去（换出）。生成的 token 不写：下一轮的 prompt 很少逐 token 包含它们（对话模板会重新渲染回复），写进去会把有用的 prompt 挤出主机层。
- **拷贝**（`tandem/csrc/kv_io.cu`）：
  - 载入（主机 → 显存）：GPU 内核直接读 mapped 内存，按层发起、每层一个 event，只开 4 个 CTA，在高优先级 stream 上；
  - 写回（显存 → 主机）：内核先把页在显存里聚成 page-first 的一块（38 MB 暂存区），再用拷贝引擎写出去，在另一条 stream 上；
  - 两个方向都先等计算 stream 上已入队的步，保证写出去的 KV 已经算完、载入的目标块不再被正在跑的步写。

### 4.2 载入和调度

- **同一步载入、按层流水**：命中主机层的请求直接在这一步入队，前向在第 i 层开始前等第 i 层的 KV（`ForwardContext.layer_waits`），载入和前向重叠；走 CUDA graph 的步在重放前等全部载完。
- **短 prefill 优先、单独成步**：复用缓存后只剩 ≤512 token 的请求，排在正在分块 prefill 的长请求和它前面的等待请求之前；剩余最少的先放，凑到 256 token 为止，这一步不带长请求的分块。放不下时，抢占剩余最多的长 prefill（换出到主机层），等它的写回完成后入队。
- **入队前检查**：等待请求只有在"主机层里的那部分前缀 + 第一块"放得下时才入队，否则整个等待，不做会被重算、而且每一步都重复的部分载入。
- **推迟调度**（late-bound scheduling，`LLMEngine.input_wait`）：overlap 调度原本在第 N 步一开始就把第 N+1 步排好，第 N 步期间到达的请求只能进第 N+2 步。现在正在跑的是 decode 步（≥10 ms）或长 prefill 步（≥512 token）时，第 N+1 步推迟到第 N 步快结束时再调度，期间一有请求到达就立即调度。步长用 CUDA event 测的 GPU 时间估计，不用墙钟时间，避免发射晚了导致估计越来越长。

## 5. 过程：每一轮发现的问题

| 轮次 | 改动 | B1 192 会话 TTFT p50 / SLO | B2 0.1 req/s TTFT p50 | 发现的问题 |
|---|---|---|---|---|
| 起点 | 只用显存 | 464 ms / 60.1% | 5.90 s | — |
| 第一轮（`6dd4427`） | 主机层第一版 | 203 ms / 95.6% | 3.26 s | 生成的 token 占满主机层；命中主机层的请求多等两三步；拷贝内核拖慢计算（无复用负载 TTFT +18%） |
| 第二轮 | 不写生成的 token；同一步按层载入；写回走拷贝引擎、载入 4 个 CTA | 146 ms / 98.4% | 3.79 s | B2 反而变差：淘汰被写回中的叶子卡住，主机层命中只载入一部分 |
| 第五轮 | 修淘汰；短 prefill 优先；推迟调度（decode 步） | 136 ms / 99.1% | 1.84 s | 命中请求被长 prefill 的分块挡住 |
| 第六轮 | 载入、写回分 stream；短 prefill 单独成步 | 133 ms / 99.0% | 1.83 s | 长 prefill 步期间到达的请求要多等一整块 |
| 最终 | 为短请求抢占长 prefill；入队前检查；推迟调度扩展到长 prefill 步 | 133 ms / 99.1% | **0.96 s** | — |

（第三、四轮在跑的过程中发现了淘汰缺陷，中途停掉，没有结果。）

- **拷贝对计算的干扰**（`benchmarks/bench_kv_io.py`）：一条 stream 连续做 BF16 4096³ 矩阵乘法，另一条同时搬 1024 页（2.4 GB）。2 个 CTA 就能跑满 PCIe；第一版每页每层一个 CTA，载入时矩阵乘法慢 4.3 倍；SM 直接往主机内存写，哪怕只用 2 个 CTA 也慢 112%，8 个以上慢 4–5 倍（推测写往 PCIe 的数据堵住了片上的写队列）。最终：载入 4 个 CTA 12.34 GB/s，矩阵乘法慢 2.4%；写回走拷贝引擎 12.6 GB/s，慢 0.9%。
- **淘汰缺陷的定位**：逐请求数据显示最热门的文档反复只命中一部分；写了离线回放脚本（真实的调度器和 radix 代码、假的主机层、同样的 96 个请求），稳定复现（命中理想的 51%，线上 52%），再打印每次请求前文档路径的状态，发现整篇都在主机层里、只是载入时显存腾不出地方。根因是淘汰遇到要写回的叶子后 `continue`，父节点永远进不了候选堆。修复后回放命中 73%。

## 6. 没完成的和下一步

| 项 | 现状 | 原因 | 可以做的 |
|---|---|---|---|
| B1 192 会话 TTFT p50 | 133 ms，目标 ≤130 | 中位数请求要新算 256–512 token，8B 上约 100 ms，是下限；推迟调度的余量（每个 decode 步的最后 25%）里到达的请求仍要多等一步 | 把余量从 25% 降到 2 倍主机发射时间（约 4 ms），估计能省 3 ms 左右；需要先验证不会造成 GPU 空转 |
| B2 剩下 4 个慢的命中请求 | 1.5–2.8 s | 挡住它们的长文档已经进入 decode，现在只抢占还在 prefill 的请求；两篇 1.7 万 token 的文档放不进 3.3 万 token 的显存 | 也抢占长上下文的 decode 请求（被抢占的请求 TPOT 会多一次约 1.6 s 的停顿） |
| B2 命中率 | 理想的 73% | 主机层只放得下约 12 篇文档，LRU 下热门文档也会被挤掉 | 按访问频率保留：离线回放在 B2 上能到 74%–76%，但会让 B1 里已结束会话的历史占着位置，需要带时间衰减 |
| B1 会话感知的预取 | 未做 | — | 按思考时间的统计，在下一轮到达前把会话的 KV 载回显存 |
| L3（NVMe） | 未做 | 这台机器的系统盘是机械硬盘，读一篇文档比重算还慢 | 换机器 |

## 7. 复现

服务器上（环境变量同 P0 基线报告 §10）：

```bash
PY=~/tandem/.venv/bin/python
T=(--engine tandem --python $PY --env LD_LIBRARY_PATH=/usr/local/gcc-11.2/lib64 --env CUDA_HOME=/usr/local/cuda-12.4
   --env PATH=/usr/local/cuda-12.4/bin:/usr/local/gcc-11.2/bin:/usr/bin:/bin --env HF_HUB_OFFLINE=1 --env TRANSFORMERS_OFFLINE=1)
B=(--model ~/models/Qwen3-8B --served-name qwen3-8b --kv-tokens 32992 --host-gb 30 --save benchmarks/results/p3-b.jsonl)
$PY benchmarks/run_reuse.py "${T[@]}" "${B[@]}" --sessions 32,96,192 --rates 0.3 --tag tandem-0.2.0.dev0-host30g-final
$PY benchmarks/run_reuse.py "${T[@]}" "${B[@]}" --runs docs --rates 0.1 --tag tandem-0.2.0.dev0-host30g-final
```

- 结果在 `benchmarks/results/p3-b.jsonl`、`p3-b-noreuse.jsonl`，逐请求记录在 `p3-b-requests.jsonl`（不进版本库）；
- 拷贝带宽和干扰：`python benchmarks/bench_kv_io.py`；
- 离线回放 B2 的缓存策略：`.transfer/b2_replay.py`（不需要 GPU）。
