# P1 对齐报告（2026-11-12）

> 对应设计方案 §8 P1：Qwen3-0.6B、Qwen3-8B BF16 通过 §1.2 的对齐判据，并产出逐算子剖析表。
>
> 对手数据沿用 P0 基线报告 §3、§4（vLLM 0.32.0、SGLang 0.5.10，过渡版本），只作开发参考，不作为对齐结论。

## 1. 结论

- **Qwen3-8B**：19 格全部达标（100%）。
  - 吞吐是最强对手的 1.00–1.01 倍。
  - 延迟比值最高 1.07，出现在 ShareGPT 并发 16 的 TPOT p99（上限 1.10）。
- **Qwen3-0.6B**：25 格中 24 格达标（96%）。
  - 吞吐是最强对手的 1.02–1.07 倍。
  - 唯一超限的是 ShareGPT 并发 32 的 TPOT p99（1.37 倍）。这一格实际测的是每档开头同时到达的那批请求的处理顺序，换 14 组提示词后与 SGLang 持平（1.02 倍），见 §4。
- 两个模型都满足 §1.2：≥90% 的格子达标，最低吞吐不低于 0.85 倍。
- **判定：P1 对齐达标**（2026-11-12 确认）。0.6B ShareGPT 并发 32 的 TPOT p99 按 §4 的分析记录，不再为它改引擎或评测方法。
- **逐算子剖析**（§5）：
  - 单路 decode 每步，0.6B 为 2.32 ms（SGLang 2.42、vLLM 2.71），8B 为 20.03 ms（SGLang 20.45、vLLM 20.25）。
  - 稳态 decode 时 GPU 空闲 0.2%–2.1%。
  - 4096 token 预填充，0.6B 为 109 ms（SGLang 119），8B 为 913 ms（SGLang 946、vLLM 909）。

## 2. 条件

- **矩阵**：同 P0 的 v1。
  - 负载：1024/256、4096/256、256/1024、ShareGPT，并发 1–32，另加 1000 条请求的离线格。
  - 每档请求数为 max(8, 4×并发)，重复 3 次，每次换一组提示词，结果取中位数。
  - 8B 只测"并发 × 单请求 token 数"不超过 KV 容量的档位，所以只有 19 格。
- **判据**（设计方案 §1.2）：每格与吞吐更高的那个对手比。
  - 吞吐 ≥0.95 倍；
  - TTFT、TPOT 的 p50 ≤1.05 倍，p99 ≤1.10 倍。
- **tandem 0.2.0.dev0**：
  - 软件：torch 2.14.1+cu126，FlashInfer 0.6.7.post2。
  - 调度：prefill 优先，token 预算 2048。
  - 执行：decode 的 CUDA Graph 捕获到 batch 64，overlap 主循环，引擎核心单独一个进程。
  - 服务参数与对手相同：max_model_len 8192，max_num_seqs 64。
- **KV 容量**：
  - 8B：三家都固定在 32,992 token（tandem 为 `--kv-cache-gb 4.5308`）。
  - 0.6B：tandem 16 GB（149,792 token），SGLang 174,674，vLLM 184,912，都远大于负载所需。
- **环境**：同一台机器、同一块卡（RTX 3090，驱动 550），压测客户端与 P0 相同（`benchmarks/bench_serving.py`）。

## 4. ShareGPT 并发 32 的 TPOT p99

**这一格测的是什么**：每档 128 个请求，p99 就是 TPOT 第二差的那个请求。

**机制**（`TANDEM_TRACE` 引擎时间线，第 2 组提示词）：
- 每档开头 32 个请求同时发出。第一个请求 23 ms 后才进入引擎，32 个到 41 ms 才全部到齐。原因是 API 进程等流式响应开始后才把请求交给引擎。
- 引擎按到达顺序分 4 步 prefill：2 个请求（首 token 在 +40 ms）、12 个（+68 ms）、5 个（+104 ms）、15 个（+133 ms）。之后每 4.1 ms 一步 decode。
- 前两步的 14 个请求拿到首 token 后，要等后面的 prefill 做完，空等 65–93 ms。其中回复很短的请求，TPOT 被这段空等拉高：
  - 6 个 token 的请求为 17.3 ms；
  - 11 个 token 的为 14.3 ms；
  - 正常 decode 只要 4–5 ms。
- SGLang 的机制相同（prefill 优先，每步 2048 token），也一样会空等。差别在于哪些请求排在前面：
  - tandem 严格按客户端发送顺序处理。
  - SGLang 进入调度器的顺序是打乱的。例如第 2 组里先处理的是第 10 号请求，第 0 号排在第三批。

**证据**：换 7 组提示词（矩阵用的是前 3 组），两家各跑两轮。

| 提示词组 | tandem 第 1 轮 | tandem 第 2 轮 | SGLang 第 1 轮 | SGLang 第 2 轮 |
|---|---|---|---|---|
| 0 | 13.62 | 14.97 | 11.58 | 16.19 |
| 1 | 8.37 | 7.41 | 8.00 | 7.63 |
| 2 | 14.40 | 14.40 | 12.16 | 9.50 |
| 3 | 11.60 | 11.89 | 13.61 | 13.78 |
| 4 | 16.92 | 18.61 | 11.98 | 14.54 |
| 5 | 19.08 | 18.83 | 16.32 | 17.07 |
| 6 | 12.82 | 12.69 | 15.07 | 20.01 |
| 中位数 | 13.62 | 14.40 | 12.16 | 14.54 |

TPOT p99，单位 ms。

- 14 组合计，tandem 中位数 14.01 ms，SGLang 13.70 ms，比值 1.02。逐组配对，tandem 在 6 组里更好。
- tandem 的顺序固定，同一组提示词两轮结果几乎一样。SGLang 两轮之间最多差 40%（第 0 组 11.58 → 16.19）。
- 矩阵里对比的 SGLang 数据是 P0 那次跑的：前 3 组为 10.11、8.27、9.09 ms，中位数 9.09。今天两轮同样 3 组，中位数是 11.58 和 9.50。
- 同一格的其余指标 tandem 都更好：吞吐 1.07 倍，TTFT p50 0.85 倍、p99 0.85 倍，TPOT p50 0.93 倍。
- 稳态下 decode 被新请求的 prefill 打断的情况（旧版对比数据）：两家频率相近（12.2% 和 11.9%）；停顿中位数 tandem 8.4 ms，SGLang 11.2 ms。

**试过但没有采用的办法**：把 token 预算提到 8192，让同一批请求并进更少的步。
- 0.6B 并发 32 只从 1.63 倍降到 1.42 倍。这批请求本来就是陆续进入引擎的，每步能并进几个请求取决于到达时间。
- 8B 1024/256 并发 8 的 TTFT p50 反而升到 1.26 倍（§6.3）。

**结论**：这一格的结果取决于开头那批请求谁先处理，3 组提示词不足以分出高下，按 14 组看与 SGLang 持平。0.6B 按矩阵结果计为 96% 达标。

4096 token 预填充（ms）：

| 模型 | tandem | SGLang | vLLM |
|---|---|---|---|
| 8B | 913 | 946 | 909 |
| 0.6B | 109 | 119 | 109 |

**解读**：
- GEMM 和 attention 基本同源：attention 上 tandem 和 SGLang 都用 FlashInfer，GEMM 三家选到的是同一批 cuBLAS 内核。所以差距主要在小算子和每步的空闲上。
- tandem 的小算子更少：QK-norm、RoPE 和 KV 写入合成了一个 Triton 内核，SGLang 是分开的几个内核。8B 单路每步比 SGLang 少 78 个内核，"其余"少约 165 µs。
- 0.6B 单路每步比 SGLang 少约 0.1 ms，约占每步的 4%，这就是 0.6B 吞吐领先的来源。
- 离 A1 的目标还远：目标是比 P0 §6 最好的对手配置（SGLang + torch.compile，0.6B 单路 TPOT 2.14 ms）快 1.3 倍，约 1.65 ms/步；tandem 现在是 2.32 ms/步。最大的一块是 GEMV 的带宽利用率（约 650 GB/s，P0 基线报告 §5.3），属于 P2 的工作。

## 6. P1 中的三处关键修正

### 6.1 调度：decode 优先改为 prefill 优先

v0.1 沿用 Sarathi-Serve 的 decode 优先：每步先排 decode，剩余预算再拿去做 prefill 分块。8B 上 TTFT 有 4 格超限（256/1024 并发 2、4、8，以及 1024/256 并发 2），达标率 79%。

- **原因**：同时到达的两个请求，第二个总是被排到下一步，而那一步还带着第一个请求的 decode。
- **另一个现象**：256 token 的 prefill 带上 1 个 decode 后，8B 上这一步多花约 24 ms。推测是 token 数从 256 变成 257，GEMM 多出一行 tile，未验证。
- **0.6B 上**：4096/256 并发 16、32 的 TPOT p50 也超限（1.14、1.24 倍）。

改为 prefill 优先（与 SGLang 默认相同）后，8B 19 格全部达标。decode 优先保留为选项：`--schedule-policy decode_first`。

### 6.2 FlashInfer `plan()` 的阻塞拷贝

剖析发现 0.6B 单路 decode 每步有一次 `cudaStreamSynchronize`（约 1.8 ms），GPU 空闲 11.9%，每步 2575 µs，比 SGLang 慢。

- **原因**：FlashInfer 0.6 的 CUDA Graph decode wrapper 在 `plan()` 里拷 `kv_indices`。这个张量在 CPU 上时，它用阻塞拷贝（只对 GPU 上的张量用非阻塞）。主机于是要等 GPU 跑完上一步才能发下一步，overlap 实际失效。
- **修正**：先把 `kv_indices` 异步拷到 GPU，再调 `plan()`。
- **效果**：0.6B 单路每步降到 2323 µs、空闲 2.1%；8B 单路从 20,114 降到 20,029 µs。0.6B 各格吞吐普遍提高 2–3 个百分点，例如 1024/256 从 SGLang 的 1.01–1.03 倍提到 1.05–1.06 倍。
- **回归测试**：`tests/test_gpu_fastpath.py::test_steps_do_not_wait_for_queued_gpu_work`。做法是先在 GPU 上排约 0.1 s 的空转，再跑一步 decode 和一步 prefill，返回时 GPU 必须仍在忙。换回旧写法后，GQA 比为 2 和 4 的模型上它都会报错。
- **排查工具**：按环节计时的开关 `TANDEM_STEP_TIMING=N`，每 N 步打印一次每步主机耗时的分布。修正后 0.6B 单路每步主机实际工作约 530 µs，其余时间在等 GPU。

### 6.3 token 预算：试过 8192，保持 2048

prefill 优先下，连续的 prefill 分块本来就是背靠背执行，所以预算大小基本不影响 decode 被打断多久，只决定同时等待的请求能并进几步。

| 格子 | 预算 2048 | 预算 8192 |
|---|---|---|
| 0.6B ShareGPT 并发 16，TPOT p99 | 1.16（旧版）→ 0.94 | 0.83 |
| 0.6B ShareGPT 并发 32，TPOT p99 | 1.37 | 1.42 |
| 8B ShareGPT 并发 16，TPOT p99 | 1.07 | 0.63 |
| 8B 1024/256 并发 8，TTFT p50 | 0.84 | **1.26** |

- 输入长度固定的负载里，一批请求总是同时开始、同时结束，下一批也就同时到达。预算大了，前面的请求要等整批 prefill 完才出首 token，TTFT p50 超限。
- 所以保持 2048。
